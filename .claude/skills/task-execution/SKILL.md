# task-execution — task 하나를 맡았을 때

브리프에 적힌 task 하나를 끝낸다. 무엇을 만드는지는 브리프가 정하고, 어떻게 만드는지는 내 방법론 스킬이 정하고, 어느 문서에 쓰는지는 `design-docs`가 정하고, 끝났는지는 다른 쪽이 판정한다. 나는 계획하고, 만들고, 자기 검증하고, 보고한다.

## 원칙

1. **시킨 것만 만든다.** 리팩터링 여지, 누락 테스트, 문서화 필요, 스타일 개선을 발견하면 보고서의 "요청 밖 발견"에 적고 손대지 않는다. 버그는 예외이며 아래 "발견한 버그"를 따른다.
2. **자기 워크트리와 소유 경로 안에서만 쓴다.** 브리프가 준 워크트리(`.worktrees/<task>`) 밖으로 나가지 않고, 그 안에서도 PATHS 밖은 읽기만 한다. `git switch`, `merge`, `push`는 하지 않는다. 다른 task의 산출물이 필요하면 보고서에 적고 리더에게 요청한다. 되돌리기 어려운 조치(삭제, 마이그레이션 실행, 외부 호출, 의존성 추가)는 브리프에 명시돼 있지 않으면 하지 않는다.
3. **입력이 있으면 그대로, 없으면 요청에서, 그래도 없으면 정하고 적는다.** 브리프의 입력 문서가 정한 것은 따른다. 문서가 정하지 않은 세부는 요청 문맥에서 읽고, 그래도 없으면 정하고 "명세에 없어 내가 정한 것"에 이유와 다른 후보를 적는다. 조용히 채우지 않는다. 결정 레벨은 `design-docs`의 표를 따른다.
   - **구현 중에는 문서를 고치지 않는다.** 구현하다 만난 세부(계약에 없는 필드 하나, 문구 하나, 엣지 케이스, 수치)는 코드와 테스트에서 정하고 보고서에 한 줄 남긴다. 문서에 넣어 달라고 멈추지 않는다. 문서는 구현이 끝난 뒤 리더가 문서 정합 task로 한 번에 맞춘다. 단, 문서가 정한 것과 **다르게** 만들지는 않는다. 문서에 없는 것을 더하는 것과 문서를 어기는 것은 다르다.
   - **막힌 것은 정말 막힐 때만.** 구조(레벨 1: 스택, 저장소, 통신 방식, 인증 모델, 에러 형식)가 문서에 없다. 만들어야 하는 동작 자체가 어느 문서에도 없다. 두 문서가 서로 모순이다. 이 셋만 "막힌 것: 입력 없음"이고, 계획 단계에서 발견해 시작 전에 보고한다. 세부 하나가 비었다고 멈추지 않는다.
4. **입력 문서가 틀렸으면 우회하지 않는다.** 문서가 정한 것이 요구와 어긋나거나 두 문서가 서로 다른 말을 하면 둘 다 인용하고 "막힌 것"에 적고 멈춘다. 문서가 정하지 않은 것과 문서가 틀린 것은 다르다.
5. **테스트를 고쳐서 통과시키지 않는다.** 테스트가 틀렸다고 판단되면 근거를 보고하고 멈춘다.
6. **부분 산출물을 되돌리지 않는다.** 실패하거나 막혀도 만든 것은 남기고 상태를 보고한다.
7. **언제든 끊길 수 있다고 가정한다.** 아래 "중단 대비"를 따른다.
8. **완료는 증거로 보고한다.** `completion-evidence` 형식. 미검증은 미검증이라 적는다.
9. **계획을 먼저 쓰고, 보고 전에 자기 검증한다.** `plan-and-check`. 보고서의 첫 버전이 계획이다.
10. **보고에는 "다음에 필요한 것"이 있다.** 이 task로 열린 것, 이 산출물을 쓰려면 있어야 하는 것. 없으면 "없음".

## 중단 대비

보고서를 마지막에 한 번 쓰지 않고 진행 중에 갱신한다.

- 의미 있는 단위를 끝낼 때마다 보고서를 덮어쓴다. 파일 하나를 완성했을 때, 테스트가 통과했을 때, 완료 기준 하나를 채웠을 때.
- 진행 중 보고서에는 맨 위에 `## 진행 상태` 절을 둔다. 끝난 것, 지금 하는 것, 남은 것, 다음 사람이 어디서 시작할지. 끝나면 지운다.
- 중단돼도 빌드가 되는 지점을 자주 만든다. 선언만 하고 파일이 없는 모듈을 오래 두지 않는다.
- 만든 것은 산출물마다 커밋한다(`git-workflow`). 중단되거나 실패해도 `wip:` 커밋으로 남긴다.

## 재개 호출일 때

**메시지로 재개된 경우.** 내 컨텍스트와 원래 브리프가 남아 있다. 메시지의 "이어서 할 것"부터 진행한다. 중단 사이에 다른 task가 파일을 만들었거나 상태가 바뀌었을 수 있으므로 이어가기 전에 지금 상태를 확인한다.

**새 인스턴스로 브리프를 받은 경우.** 브리프에 "중단 재개"가 있으면 이미 만든 것이 디스크에 있다.

- 지우고 새로 시작하지 않는다. 남은 부분만 이어서 완성한다.
- 기존 코드와 보고서의 `## 진행 상태`를 먼저 읽고 무엇이 끝났는지 파악한다.
- 기존 설계를 따른다. 갈아엎는 것은 요청 밖 수정이다.
- 빌드가 깨져 있으면 그것부터 복구한다.
- 브리프의 상태 기술을 그대로 믿지 않는다. 빌드·테스트를 직접 돌려 확인한다.

## 발견한 버그

요청하지 않은 버그를 만나면 관련성으로 가른다. 아래 중 하나라도 맞으면 관련 있음이다.

- 내 소유 경로 안에 있다
- 이걸 고치지 않으면 내 완료 기준을 만족할 수 없다
- 내가 이번에 바꾼 코드가 드러냈다
- 내가 만든 것과 같은 원인이고 그중 한 곳이 내 소유 경로다

관련 있으면 같이 고친다. 재현 → 원인 → 최소 수정 → 증명 순서이고, 소유 경로 안에서만 고친다. 원인이 경로 밖이면 고치지 않고 관련 없음으로 보고한다. 고친 것은 보고서의 "같이 고친 버그" 절에 적는다. 이 절에 없는데 바뀐 파일은 범위 이탈로 잡힌다.

관련 없으면 손대지 않는다. "요청 밖 발견"에 증상, 위치, 재현 여부를 적는다. 판단이 애매하면 관련 없음으로 둔다.

## 조사 위임

라이브러리·프레임워크의 사용법과 API는 기억으로 쓰지 않고 context7(`resolve-library-id` → `query-docs`, 버전 명시)으로 현재 문서를 읽는다. 한 번 조회한 결과 중 이후에도 필요한 것은 보고서나 산출물 문서에 옮겨 적고 다시 조회하지 않는다.

코드베이스 구조, 기존 컨벤션, 외부 문서처럼 읽을 것이 많으면 `investigator`를 부른다(`Agent`, `subagent_type: investigator`, 브리프는 `QUESTION / SCOPE / EXPECTED OUTCOME`). 여러 질문은 여러 investigator를 동시에 던진다. 그 밖의 에이전트는 부르지 않는다. 쓰기 task를 만들지 않는다.

## 재작업 호출일 때

브리프에 `round`와 finding ID 목록이 있으면 재작업이다. 같은 워크트리에서 이어서 한다.

- 리뷰 파일 원문을 읽는다.
- 나열된 ID만 고친다. 다른 것은 발견해도 손대지 않는다.
- ID별로 무엇을 어떻게 고쳤는지 보고서에 적는다. 고치지 않기로 한 ID는 이유(명세 근거, 기준 오류)를 적는다.
- 고친 뒤 원래 완료 기준 전체를 다시 검증한다.
- **재작업은 한 번뿐이다.** 두 번째 검사도, 두 번째 재작업도 없다. 나열된 ID 전부를 이번에 끝낸다. ID마다 "무엇을 어떻게 고쳤고 어디를 보면 확인되는지"를 보고서에 적는다. 리더가 그 설명을 파일과 대조해 닫는다. 설명이 없는 ID는 안 고친 것으로 처리된다.
- 문서를 고칠 때는 지적된 부분을 다시 써서 처음부터 그렇게 쓰인 문서가 되게 한다. 문서 안에 finding 번호, 라운드, "반영했다"는 말을 남기지 않는다. ID별 설명은 보고서에만 쓴다. 변경 이력 표에는 날짜와 내용 한 줄. `docs-lint.py docs <파일>`을 돌려 통과를 확인한다. 리더의 `set done`이 같은 검사를 다시 돌리고 위반이 있으면 거부한다.

## 산출물의 경계

- **`docs/`는 사용자가 받는 최종 산출물이다.** 작업 기록(task ID, finding 번호, 라운드, 에이전트 이름, `_tasks/` 경로, "반영"·"재작업" 같은 말, 템플릿 안내문)을 `docs/`에 남기지 않는다. 그런 것은 전부 보고서(`_tasks/<run>/reports/<task>.md`)에 쓴다. 문서를 커밋하기 전에 `.claude/skills/design-docs/scripts/docs-lint.py docs <파일>`을 돌린다. 위반이 있으면 리더가 done을 거부한다.
- **코드 주석은 그 자리에서 이해돼야 한다.** 주석은 이 코드가 무엇을 왜 하는지를 문장으로 적는다. `# BR-04`, `// FSD §3.2 참조`, `/* ADR-003 */`처럼 문서 참조만 있는 주석은 주석이 아니다. 문서 링크는 설명 뒤에 "더 자세한 것은 …"의 참고로만 둔다. 읽는 사람이 문서를 열지 않고도 코드를 이해할 수 있어야 한다.

  ```python
  # 나쁨
  if days > 90:  # BR-04
      raise ValidationError()

  # 좋음
  # 조회 기간은 90일까지다. 그 이상은 보관소로 넘어가 이 API로는 볼 수 없다.
  # 참고: docs/fsd/orders/REQ-01-order-search.md BR-04
  if days > 90:
      raise ValidationError()
  ```

  커밋 전에 `docs-lint.py code <소유 경로>`를 돌린다. 리더가 확인할 때 같은 검사를 돌린다.

## 도구 출력

테스트·빌드 출력은 실패 부분만 읽는다. 조용한 옵션과 `tail`을 쓰고 전체 로그를 컨텍스트에 넣지 않는다. diff는 `--stat`을 먼저 보고 필요한 파일만 연다.

## 보고

산출물마다 자기 워크트리에서 커밋한다. 커밋 뒤 `git show --name-only`로 소유 경로 밖 파일이 없는지 확인하고, 마지막 커밋 해시를 보고서에 적는다.

보고서 위치는 `_tasks/<run>/reports/<task>.md`, 형식은 `completion-evidence`. 절은 완료 기준 표 / 변경한 파일 / 같이 고친 버그 / 명세에 없어 내가 정한 것 / 요청 밖 발견 / 막힌 것 / 다음에 필요한 것. 그 앞에 `plan-and-check`의 자기 검증 표.

마지막 응답에는 보고서 경로, 완료 기준 표, 다음에 필요한 것만 옮긴다. 설명 문장을 붙이지 않는다. 리더는 파일을 읽는다.

원장(`tasks.json`)은 건드리지 않는다.

## 멈춰야 하는 신호

- 소유 경로 밖을 바꿔야 완료된다
- 되돌리기 어려운 조치가 필요하다
- 입력 문서 두 개가 서로 다른 것을 말한다
- 구조(레벨 1) 결정이 문서에 없다. 레벨 2 세부가 빈 것은 멈출 일이 아니다
- 같은 접근을 세 번 바꿔 시도했는데 안 된다
- 테스트를 고쳐야 통과할 것 같다

이럴 때는 진행하지 말고 상태를 보고서에 적고 끝낸다.
