# interface-contract — 계약을 먼저 확정하고, 양쪽은 계약에 대조한다

## 원칙

1. **계약은 구현보다 먼저 done이 된다.** 계약 task가 리뷰를 통과한 뒤에야 의존 task가 시작한다.
2. **모든 요청·응답에 실제 값이 들어간 예시를 붙인다.**
3. **표기를 하나로 정한다.** 필드명 표기(camelCase / snake_case), 날짜 형식, 시간대, null과 빈 값의 구분, 불리언 표현, ID 형식. 계약 상단에 한 번 적고 전체가 따른다.
4. **에러도 계약이다.** 에러 코드, HTTP 상태, 응답 본문 형식, 어떤 입력이 어떤 에러를 내는지.
5. **없는 것을 없다고 적는다.** 페이지네이션 없음, 정렬 없음, 인증 없음.
6. **바꾸면 버전을 올리고 영향을 적는다.** 이 계약을 이미 쓴 산출물이 있으면 다시 봐야 한다는 것을 보고에 올린다.

## API 스펙

문서 템플릿 `api.md`로 쓴다.

## 공유 타입·스키마일 때

- 타입 파일 자체가 계약이다. 소유 경로는 그 파일이고, 의존 task는 import만 한다.
- 데이터베이스 스키마는 정의와 마이그레이션이 한 task. 마이그레이션 **실행**은 되돌리기 어려우므로 브리프가 명시할 때만.

## 계약을 읽고 구현하는 쪽

- 계약에 없는 필드를 만들지 않는다. 필요하면 "명세에 없어 내가 정한 것"이 아니라 **"막힌 것"**으로 올린다.
- 계약의 예시 값으로 테스트를 만든다. 예시가 곧 픽스처다.
- 목 데이터는 계약의 예시를 그대로 쓴다.

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 목록 순회 중 오류 | 한쪽은 `{items:[]}`, 다른 쪽은 배열 기대. 예시 없이 설명만 |
| 날짜가 하루 어긋남 | 시간대 미정 |
| 이미지가 안 보임 | `thumbnailUrl` vs `thumbnail_url`. 표기 규칙 없음 |
| 에러 화면이 안 뜸 | 에러 형식이 계약에 없어 화면이 다른 형태를 기대 |
| 통합 시 필드 세 개 추가됨 | 구현하면서 계약을 고침. 다른 쪽은 옛 계약 |
| 목과 실제가 다른 값 | 목 데이터를 계약 예시가 아닌 값으로 만듦 |
