# ci-cd — 요구할 때만 만들고, 로컬에서 검증 가능한 만큼만 완료로 친다

요구가 있을 때 task 하나로 만든다. 다른 코드 task와 같은 규칙(소유 경로, 완료 기준, 리뷰)을 따른다.

## 완료 기준

CI task의 완료 기준은 "CI 통과"가 아니라 **"CI가 실행할 명령이 로컬에서 전부 통과"**다. CI 자체의 실행 결과는 사용자가 푸시한 뒤 사후 확인이고, 보고에 "CI 실행은 미검증(푸시 전)"으로 적는다. 이걸 "CI 통과"로 적으면 거짓이다.

## 절차

1. **저장소의 명령을 정본으로.** 빌드·테스트·린트·타입체크 명령은 `package.json`, `Makefile`, `pyproject.toml` 등 저장소가 이미 정한 것을 쓴다. CI 파일에 명령을 새로 만들지 않는다.
2. **단계를 나눈다.** 설치 → 정적 검사 → 테스트 → 빌드 → (요구 시) 산출물. 각 단계가 독립적으로 실패를 보고하게.
3. **트리거는 저장소의 브랜치 관례를 따른다.** 관례가 없으면 기본 브랜치 push와 PR. 브랜치 전략을 CI 파일이 정의하지 않는다.
4. **시크릿은 이름만.** 값은 사용자가 등록한다. 필요한 시크릿 목록을 보고에.
5. **로컬에서 같은 명령을 순서대로 돌린다.** 이것이 실행 검증이다.

## 컨테이너·배포 설정일 때

- Dockerfile은 로컬 빌드 성공이 완료 기준. 데몬이 없으면 미검증으로.
- 배포 스크립트는 **실행하지 않는다.** dry-run 옵션이 있으면 그것까지. 실제 배포는 사용자.
- 환경 변수는 `.env.example`류에 이름과 설명만. 값은 넣지 않는다.

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 로컬은 되는데 CI 실패 | CI 파일의 명령이 저장소 스크립트와 다름 |
| "CI 통과"로 보고했는데 안 돌아감 | 푸시 전 미검증을 통과로 적음 |
| 브랜치 바꾸니 CI가 안 뜸 | CI 트리거가 브랜치명을 하드코딩 |
| 배포가 실행돼 버림 | 스크립트를 검증한다며 실행 |
