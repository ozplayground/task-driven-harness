# architecture — 결정 사슬 순서로 정한다

입력은 요구, NFR·제약, 조사 결과. 산출물은 구조·스택·횡단 규약과 그 결정의 기록, 후속 필수 설계 목록. 정하지 않는 것은 개별 기능의 동작, 모듈 내부, task 분할.

## 첫 호출 — 결정 범위와 조사 목록

답할 것은 셋이다.

1. **이번에 정할 것.** 결정 사슬 중 이 요구가 건드리는 항목. 기존 구조 문서와 결정 기록이 덮는 항목은 그 절·결정의 경로를 근거로 댄다.
2. **정하려면 무엇을 알아야 하나.** 정할 것마다 **조사 목록** — 질문 하나에 조사 하나, 비교가 필요하면 벤치마크로 표시. 기억으로 정하지 않는다.
3. **사용자에게 물어야 할 것.** 결정을 가르는 NFR·제약 중 요구에 없는 것.

이 시점에 결정하지 않는다.

## 결정 사슬

위에서 아래로. 아래 결정은 위 결정에 묶인다. 위가 바뀌면 아래를 다시 본다.

| # | 결정 | 답해야 하는 질문 | 앞에 묶이는 것 |
|---|---|---|---|
| 0 | NFR·제약 | 규모(사용자·데이터량·처리량), 지연·가용성, 오프라인·실시간 여부, 팀 규모·역량, 예산, 기존 시스템, 규제 대상 데이터 | 요구, compliance |
| 1 | 구조 스타일 | 모놀리스 / 모듈러 모놀리스 / 서비스 분리, 그리고 **어느 부분을** 비동기·이벤트로 | 0. 동기 경로와 비동기 경로가 한 시스템에 공존한다 |
| 2 | 통신 | 동기 프로토콜, 1에서 비동기로 둔 부분의 큐·스트림, 이벤트 스키마·버전, 멱등성, 재처리 | 1이 비동기를 안 두면 없음. 처리량은 0에서 |
| 3 | 데이터 | 모듈별 데이터 소유권, 저장소 종류별 선택(관계형·시계열·문서·파일·캐시), 보존·삭제 | 1의 경계, 0의 데이터량, compliance |
| 4 | 횡단 규약 | 인증·권한 모델, 에러 응답 형식, 설정·시크릿, 로깅·추적·지표, 시간·단위·로케일 | 1·2·3 |
| 5 | 특수 요구 | 검색, AI·추론, 실시간, 파일·미디어, 지리, 결제 같은 요구마다 — **먼저 유스케이스를 규칙·기존 기능으로 풀 수 있는지** 묻고, 안 되면 기술을 고른다. RAG는 LLM 유스케이스가 있고 근거 데이터가 필요할 때만 | 3의 저장소와 겹치는지 |
| 6 | 언어·프레임워크·런타임 | 위 스택을 잘 지원하나, 팀이 다루나 | 1~5 |
| 7 | 배포 형태 | 환경, 실행 단위, 인프라 종류, IaC 위치 | 1·6 |
| 8 | 저장소 구조 | 모노·멀티, 최상위 디렉토리, 모듈 경계와 디렉토리 대응 | 1·6 |

기존 저장소면 0~8을 **있는 그대로** 적는다(as-is, 코드 위치 근거). 그 뒤 요구가 바꾸는 항목만 "변경" 절에 쓴다. 있어야 할 것을 있는 것처럼 쓰지 않는다.

## 결정 하나의 기록

되돌리기 어려운 결정 하나에 기록 하나.

```markdown
## 맥락
무엇이 이 결정을 요구하나. 관련 NFR 수치.

## 대안
| 대안 | 장점 | 단점 | 근거 (조사 결과의 위치) |

## 기준
무엇으로 고르나 (처리량, 운영 역량, 비용, 되돌리기 비용).

## 결정
무엇을. 추천이면 "추천: A" — 확정은 사용자.

## 결과
이 결정이 강제하는 것(후속 설계, 계약), 막는 것.

## 재검토 조건
언제 이 결정을 다시 보나. 미룬 결정이면 여기가 본문이다.
```

머리말 `status`는 `proposed → decided | deferred | superseded`, `decided_by`는 사용자. 대안이 하나뿐인 기록은 완료가 아니다. 대안이 정말 없으면 "왜 없는가"를 대안 표 자리에 쓴다.

## 되돌릴 수 있으면 미룬다

기준은 하나 — 바꾸면 만든 것을 다시 만들어야 하는가. 아니면 `deferred`로 두고 재검토 조건만 남긴다. 검색 엔진(작게 시작), 캐시 계층, 특정 라이브러리는 대개 미룰 수 있다. 저장소 종류, 통신 방식, 인증 모델, 모듈 경계는 대개 못 미룬다.

## 구조 문서의 절

```markdown
## 요약 (10줄)
## NFR·제약 (표, 수치)
## 시스템 구성 (구성 요소, 경계, 통신, 데이터 흐름)
## 저장소 구조
## 스택 (계층별 표: 선택, 결정 기록 링크)
## 횡단 규약 (인증, 에러 형식, 설정, 로깅·추적, 단위·시간)
## 데이터 소유권 (모듈 ↔ 데이터)
## 배포 형태
## 결정 목록 (id, 주제, status)
## 후속 필수 설계 (이 구조가 강제하는 문서와 각각의 입력)
## 변경 이력
```

**"후속 필수 설계"**: 이벤트를 택했으면 이벤트 계약이 구현 전 필수, 시계열을 분리했으면 데이터 모델이 필수. 코드 규칙·로컬 실행 방법도 여기서 같이 낸다.

## 둘째 호출 — 결정 초안

조사 결과를 읽고 사슬 순서대로 결정 기록 초안(`proposed`)과 구조 문서 초안을 쓴다. 각 결정에 추천을 적되 확정하지 않는다. 후속 필수 설계 목록(문서마다 입력과 선행 관계)과 모듈 경계·데이터 소유권을 분명히 적는다.

## 완료 기준

- 사슬 0~8 각각이 결정·deferred·해당 없음 중 하나로 채워짐
- 되돌리기 어려운 결정마다 기록이 있고 대안 ≥2, 기준, 근거 출처
- 후속 필수 설계 목록이 있음
- as-is라면 코드 위치 근거

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 프레임워크 이름이 문서 첫 줄 | 6을 먼저 정함 |
| "마이크로서비스" 또는 "모놀리스" 하나로 끝 | 1을 전부 아니면 전무로 봄. 비동기 경로를 안 나눔 |
| RAG·벡터 DB가 정해졌는데 유스케이스가 없음 | 5에서 유스케이스 질문을 건너뜀 |
| 결정 기록의 대안이 하나 | 결정이 아니라 선호 |
| 구현자가 "에러 형식을 내가 정했다" | 4 횡단 규약 누락 |
| "기존 구조가 덮는다"인데 근거 경로가 없음 | 기억으로 답함 |
| 끝나지 않음 | 미루기 규칙 미사용 |
