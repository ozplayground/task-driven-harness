# frontend-work — 명세의 화면을 저장소의 방식으로

입력은 명세(무엇을 보여주고 어떻게 동작하는가), 계약(데이터가 어디서 오는가), 구조 문서(인증·에러 형식·횡단 규약), 코드 규칙(이 저장소는 어떻게 만드는가). 산출물은 그것들대로 동작하는 화면과 그 테스트. **정하지 않는 것은 위 넷이다.** 브리프의 입력 문서 중 이 task에 필요한 것이 없으면 만들지 않고 계획 단계에서 "막힌 것: 입력 없음"으로 보고한다.

## 시작 전에

0. **입력 문서를 전부 연다.** 하나라도 없고 이 task가 그것을 필요로 하면 여기서 멈춘다.
1. **저장소의 방식을 먼저 본다.** 프레임워크, 라우팅 방식, 상태 관리, 스타일링, 컴포넌트 배치, 테스트 도구. 기존 화면 하나를 끝까지 읽는다 — "이 저장소에서 화면 하나는 어떤 파일들로 구성되는가"에 답할 수 있어야 한다. 새 방식을 들여오지 않는다.
2. **명세에서 이 task의 화면만 뽑는다.** 화면별로 상태 목록을 만든다. 로딩, 비어 있음, 에러, 권한 없음, 정상. 명세가 안 정한 상태는 "명세에 없어 내가 정한 것"에 적는다.
3. **계약의 예시를 목 데이터로 쓴다.** API가 아직 없어도 계약 예시로 화면을 만들 수 있다. 계약에 없는 필드를 화면이 기대하면 안 된다.

## 만들 때

- **한 화면의 상태를 전부 만든다.** 정상 경로만 만들고 에러·빈 화면을 빼면 완료 기준 미달이다. 해당 없는 상태는 보고에 "해당 없음 — 이유".
- **입력 검증은 명세의 규칙 그대로.** 메시지 문구도 명세에 있으면 그대로. 없으면 정하고 보고.
- **API 호출은 계약의 형태 그대로.** 필드명 변환이 필요하면 한 곳(어댑터)에서만. 화면 여기저기서 바꾸지 않는다.
- **소유 경로 밖의 공용 컴포넌트를 고치지 않는다.** 필요하면 소유 경로 안에 만들거나 "막힌 것"으로 보고.
- **접근성 기본은 지킨다.** 폼 요소에 라벨, 버튼은 버튼, 이미지에 대체 텍스트. 명세가 안 시켜도 한다.

## 검증

| 확인 | 방법 |
|---|---|
| 렌더·상태 전환 | 컴포넌트 테스트 또는 브라우저. 브라우저가 없으면 테스트로, 그것도 없으면 미검증 명시 |
| 계약 준수 | 호출부가 기대하는 필드 ↔ 계약 예시. 하나씩 |
| 명세 준수 | 화면별 상태·검증 규칙 ↔ 명세 항목(ID) |
| 기존 화면 영향 | 전체 테스트·빌드·타입체크 |

"화면이 뜬다"는 실행 검증이 아니다. 명세의 동작(입력 → 결과)을 실제로 해 본 것이 실행 검증이다.

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 목으로는 되는데 실제 API로는 깨짐 | 목 데이터를 계약 예시가 아닌 임의 값으로 만듦 |
| 새 화면만 다른 스타일 | 기존 화면을 안 읽고 새 방식으로 만듦 |
| 에러 시 빈 화면 | 상태 목록을 안 만들고 정상 경로만 구현 |
| 공용 버튼 고쳐서 다른 페이지 깨짐 | 소유 경로 밖 수정 |
| "명세 FR-03 화면 없음" 지적 | 명세에서 이 task의 화면 목록을 안 뽑음 |
