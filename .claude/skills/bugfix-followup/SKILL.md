# bugfix-followup — 남은 버그를 끝에 모아 처리한다

여기서 다루는 것은 **관련이 없어 손대지 않고 보고만 한 버그**다. 계획된 task가 전부 끝난 뒤 한자리에 모아 처리한다. 작업 중간에 끼워 넣지 않는다.

## 절차

### 1. 모은다

보고의 "요청 밖 발견"에서 **버그·결함만** 골라 진행 기록에 적는다. 출처 task, 위치, 증상, 재현 여부. 리팩터링 여지·누락 테스트·문서화 필요는 버그가 아니므로 이 목록에 넣지 않는다. 그것들은 최종 보고에 별도로 올린다.

이 시점에 task로 만들지 않는다. 계획된 task가 도는 중에는 목록만 자란다.

### 2. 올린다

모든 계획된 task가 `done`이 되면, 종료 보고 **전에** 목록을 표로 올린다.

```
계획된 task 전부 완료. 작업 중 발견돼 손대지 않은 버그 3건:

| 출처 | 위치 | 증상 | 재현 |
|---|---|---|---|
| T2 | src/api/users/handler.ts:41 | null 체크 누락으로 특정 요청에서 500 | 있음 |
| T3 | src/utils/date.ts:12 | 월말 날짜가 하루 밀림 | 있음 |
| T3 | src/api/auth/token.ts | 만료 토큰이 통과하는 것으로 보임 | 없음 (추정) |

버그픽스 task로 처리할까요? 전부 / 일부 지정 / 하지 않음
```

재현이 없는 항목은 "추정"으로 표시한다. 사용자가 그것도 처리하라고 하면 그 task의 첫 완료 기준은 "재현 가능한지 판정"이고, 재현이 안 되면 그 사실이 결과다.

### 3. 추가한다

사용자가 지정하면 **같은 run에** task를 추가한다. 새 run을 만들지 않는다.

```bash
python3 $L add <run> B1 --title "users 핸들러 null 체크" --paths "src/api/users/**,tests/api/users.*" --accept "재현 절차가 통과로 바뀐다" --accept "전체 테스트 통과"
python3 $L validate <run>
```

- id는 `B1`, `B2`처럼 계획된 task와 구분되게 붙인다.
- 소유 경로는 리더가 정한다. 여러 건이 겹치면 한 task로 묶고, 안 겹치면 나눠서 동시에 돈다.
- 완료 기준의 첫 항목은 항상 **"재현이 통과로 바뀐다"**이다. "코드를 고쳤다"는 완료가 아니다.
- 다른 버그픽스 task와 경로가 겹치면 `validate`가 잡는다. 의존을 걸거나 묶는다.

### 4. 실행한다

계획된 task와 완전히 같다. 브리프, 실행, 리뷰, 재작업 2회 상한.

### 5. 멈춘다

**버그픽스 task가 실행 중에 낸 새 발견은 보고만 한다.** 관련성 판정도 하지 않고, 자동으로 다음 버그픽스 task가 되지도 않는다. 최종 보고에 목록으로 올리고 run을 끝낸다.

깊이 1이 상한이다. 남은 것은 사용자가 새 요청으로 시작한다.

## 이 스킬이 붙지 않으면

모은 목록을 최종 보고에 올리기만 하고 끝낸다. 사용자가 그때 시키면 새 요청이 된다.

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 원래 요구가 언제 끝났는지 모르겠음 | 버그픽스를 중간에 끼워 넣음. 계획된 task 전부 done 뒤에 |
| 버그픽스 task 둘이 같은 파일 충돌 | 경로를 안 나누고 발견 단위로 그대로 만듦 |
| 없던 버그를 "고침" | 재현 없는 추정을 그대로 수정 대상으로 |
| run이 끝나지 않음 | 버그픽스가 낸 발견을 또 task로. 깊이 1 |
| 리팩터링까지 버그픽스로 들어감 | 목록에 버그만 넣는 규칙을 안 지킴 |
