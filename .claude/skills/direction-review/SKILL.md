# direction-review — 문서를 비평하고 계획을 비판한다

두 가지 일을 한다. 문서가 나오면 그 문서의 내용을 비평한다. 구현을 시작하기 전에는 계획을 비판한다. 둘 다 고치지 않고 항목만 낸다.

## 문서 비평

문서를 처음부터 끝까지 읽는다. 절이 갖춰졌는지가 아니라 적힌 내용이 맞는지를 본다. 읽으면서 아래 여섯 가지를 묻고, 걸리는 것을 항목으로 적는다.

| 종류 | 묻는 것 | 예 |
|---|---|---|
| 과잉 설계 | 요구에 비해 지나치게 복잡한가. 지금 필요 없는 계층, 추상화, 인프라, 확장 여지가 들어 있나 | 사용자 30명인데 서비스를 셋으로 나누고 메시지 브로커를 둠 |
| 불필요한 기술 | 요구가 없는데 쓴 기술, 라이브러리, 인프라가 있나. 이미 있는 것으로 될 일을 새것으로 하나 | 캐시 요구가 없는데 Redis를 넣음. PostgreSQL로 되는 큐를 별도 브로커로 |
| 근거 부족 | 기술 스택, 버전, 수치, 규칙을 왜 그렇게 정했는지 이유가 있나. 이유가 요구나 조사에서 왔나, 아니면 "익숙해서"인가 | "PostgreSQL 16"만 있고 왜 16인지 없음. 재시도 5회의 출처 없음 |
| 누락 | 이 문서가 정했어야 하는 레벨의 결정이 빠져 있나(문서 표준의 결정 레벨 표). 뒤 작업이 짐작으로 채워야 하는 곳이 있나 | 스택 표에 버전이 없음. FSD에 오류 문구가 없음. 배포 문서에 롤백이 없음 |
| 모순 | 상위 결정이나 같은 층의 다른 문서와 어긋나는 곳이 있나 | 아키텍처는 UTC 저장인데 데이터 모델은 KST |
| 요구 대비 | 요구를 받아내지 못한 곳, 요구에 없는 것을 넣은 곳이 있나 | REQ-03이 어느 기능에도 없음. 요구에 없는 관리자 대시보드가 들어감 |

문서 종류마다 특히 볼 것이 있다.

- 아키텍처, 결정 기록: 스택의 선택과 버전마다 이유가 있는지. 대안을 실제로 비교했는지, 기준이 결정보다 먼저 있었는지. 미룬 결정에 다시 볼 조건이 있는지.
- PRD: 제외 범위가 있는지. 인수 조건이 판정 가능한 문장인지. 비기능 요구가 수치인지.
- FSD: 구현하는 사람이 정해야 할 것이 남았는지(문구, 기본값, 권한, 경계). 인수 조건마다 받는 기능이 있는지.
- 데이터 모델, 계약: 상위 문서(아키텍처, FSD)와 이름·타입·규약이 같은지. 없는 것을 없다고 적었는지.
- 테스트 계획: 모든 요구와 비기능 요구가 어떤 테스트로 확인되는지, 제외했다면 이유가 있는지.
- 조사: 근거 등급이 주장을 받쳐 주는지. 반대 근거를 찾아봤는지.

사용자가 정한 것(결정 기록에 확정한 사람이 사용자)은 다시 열지 않는다. 다만 사용자가 이름만 정하고 버전이나 범위를 정하지 않았다면 그 빈 부분은 누락으로 본다.

## 계획 비판

구현 task를 투입하기 전에 한 번 한다. 계획이 참이라고 가정한 것마다 근거를 묻는다.

| 종류 | 묻는 것 | 예 |
|---|---|---|
| 완료 기준 | 이 기준을 전부 통과해도 요구가 안 될 수 있나 | "테스트 통과"만 있고 REQ-05 동작 기준 없음 |
| 선행 누락 | 결정이나 문서 없이 만들 수 없는 task가 있나 | 계약 없이 화면·API 동시 투입 |
| 경계 | task 분할이 구조의 경계·데이터 소유권과 맞나 | 한 task가 두 모듈의 데이터를 씀 |
| 범위 | 요구에 없는 것이 들어왔나, 요구가 빠졌나 | wanted 3개인데 task는 2개만 덮음 |
| 조사 결손 | 결정에 필요한 조사가 빠졌거나 근거가 의견뿐인가 | 큐 선택의 근거가 블로그 |

## 비판 파일

문서 템플릿 `critique.md`로 쓴다. 항목마다 번호, 종류, 심각도, 대상, 내용, 확인 방법을 적는다. 확인 방법은 리더가 따라가 사실인지 볼 수 있는 것이어야 한다.

| 심각도 | 기준 |
|---|---|
| blocker | 이대로 가면 요구를 만족하지 못하거나, 되돌리기 어려운 결정이 근거 없이 내려지거나, 뒤 작업이 짐작으로 만들어야 한다 |
| major | 실행 중 재작업이나 재계획을 일으킬 가능성이 높다. 필요 없는 기술이나 계층이 들어가 유지 부담이 생긴다 |
| minor | 알아 두면 좋음. 반영 여부는 처리하는 쪽 재량 |

## 처리하는 쪽의 절차

내용을 판단하지 않는다. 항목을 갈라서 보낸다.

1. 비판 파일을 읽는다. 원문.
2. 항목마다 셋 중 하나를 기록에 적는다.
   - 형식·덮음 문제(요구가 어느 task에도 없음, 입력 문서 누락, 범위 불일치) → 리더가 직접 task 표를 고친다
   - 내용 문제(과잉 설계, 불필요한 기술, 근거 부족, 누락, 모순, 대안) → 문서를 쓴 에이전트의 재작업 task에 번호를 넘겨 반박 또는 수정을 받는다. 리더가 자기 의견으로 닫지 않는다
   - 근거 부족 → 조사 task를 추가해 근거를 만든 뒤 문서를 쓴 쪽이 다시 정한다
   - 요구 자체가 모호한 것 → 유인이면 사용자에게, 무인이면 조사 task(비슷한 제품 벤치마크)로 요구를 정의한다
3. 문서를 쓴 쪽이 고치면 round 2. round 2는 이전 항목의 해소 여부를 보고, 새 항목은 고치다 생긴 것과 blocker만.
4. 왕복 2회. 그래도 blocker면 유인이면 사용자에게 열린 항목과 함께 올리고, 무인이면 조사 task를 추가해 근거를 만든 뒤 한 번 더 돈다.
5. 승인을 요청할 때 "비판 요약: P-C1 반영, P-C2 반영(조사 추가), P-C3 기각(이유)"을 붙인다.

## 비판하는 쪽이 하지 않는 것

- 계획·문서를 고쳐 쓰기. 비판만 한다
- 새 요구 만들기. "이것도 있어야"는 요구가 아니라 제안이고 minor다
- 사용자가 결정한 것 다시 열기
- round 2에 새 major·minor 올리기
- 취향. 다른 방식이 더 마음에 든다는 것은 항목이 아니다. 요구, 근거, 필요성으로 말한다
