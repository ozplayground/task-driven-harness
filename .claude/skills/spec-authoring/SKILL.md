# spec-authoring — 뒤에서 만들 사람이 결정을 내리지 않게 쓴다

입력은 아이디어·요구·조사 결과·구조 문서. 산출물은 무엇을 만드는지의 정의. 정하지 않는 것은 어떻게 만드나(구조·스택·계약).

## 어떤 문서를 쓰는가

사용자가 요구한 것만 쓴다. "PRD 써줘"면 PRD만. "PRD랑 FSD"면 둘. 그 사이의 문서(요구사항 정의서 등)는 요구했을 때만 만든다. 사용자가 이미 문서 형식을 갖고 있으면 그 형식을 따른다. 없을 때만 아래 골격을 쓴다.

| 문서 | 답하는 질문 | 최소 절 |
|---|---|---|
| **제품 개요 / PRD** | 누가, 왜, 무엇을. 무엇은 안 하는가 | 배경·문제, 대상 사용자, 목표와 측정, 범위(포함/제외), 핵심 기능 목록(우선순위), 제약, 열린 질문 |
| **요구사항** | 시스템이 무엇을 해야 하는가 | 기능 요구(ID 부여), 비기능 요구, 인수 조건 |
| **기능 명세(FSD)** | 각 기능이 정확히 어떻게 동작하는가 | 기능별: 트리거, 입력과 검증 규칙, 상태와 전이, 정상 흐름, 예외·에러(무엇이 보이는가), 권한, 데이터 변경, 화면에 안 보이는 규칙 |
| **설계 문서** | 왜 이렇게 만들어야 했는가 | 결정과 근거, 고려한 대안, 영향 범위, 되돌리는 방법 |
| **용어집** | 이 도메인의 말을 무엇이라 부르나 | 용어, 정의, 동의어(쓰지 않을 말), 코드·필드에서의 이름 |
| **레퍼런스·가이드** | 외부 독자가 이걸 어떻게 쓰나 | 계약에서 도출. 시작하기, 인증, 엔드포인트별 예시, 에러, 한도. 계약과 어긋나면 계약이 정본 |

## 절차

1. **입력을 읽는다.** 사용자의 아이디어·문서·기존 코드. 있는 것을 다시 묻지 않는다.
2. **범위 경계를 먼저 적는다.** 포함보다 **제외**가 중요하다.
3. **기능마다 ID를 붙인다.** `FR-01` 같은 짧은 것.
4. **결정을 미루지 않는다.** 정보가 부족하면 임시 결정을 내리고 `[가정]`으로 표시하고 근거를 적는다. 단, 되돌리기 어려운 결정(저장 방식, 인증, 공개 API 형태)은 `[결정 필요]`로 표시하고 완료 보고의 "막힌 것"에 올린다.
5. **해당 없음도 적는다.** 상태·에러·권한 절이 비면 "해당 없음 — 이유".
6. **검증 가능하게 쓴다.** "빠르게 응답한다" 대신 "목록 조회 1초 이내". "적절히 처리" 대신 무엇이 보이고 무엇이 저장되는지.
7. **사용자가 준 문서를 보강할 때**는 원문을 고치지 않고 덧붙인다. 바꿔야 하면 바꾼 곳과 이유를 문서 상단에 표로.

## 기능 명세 항목 점검

기능 하나마다 아래가 있는지 본다. 없으면 적거나 "해당 없음 — 이유".

- 트리거 (누가 언제 시작하는가)
- 입력과 각 입력의 검증 규칙 (형식, 범위, 필수 여부, 실패 시 메시지)
- 상태와 전이 (있다면 표로)
- 정상 흐름 (단계별)
- 예외와 에러 (무엇이 일어나고 사용자에게 무엇이 보이는가)
- 권한 (누가 할 수 있는가, 아니면 무엇이 보이는가)
- 데이터 변경 (무엇이 만들어지고 바뀌고 지워지는가)
- 화면에 안 보이는 규칙 (보존, 동기화, 배치, 한도)

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 구현자가 "명세에 없어 내가 정한 것"을 열 개 보고 | 검증 규칙·에러·권한 절이 비어 있음 |
| "명세와 다르다"를 판정할 수 없음 | 기능에 ID가 없어 대조할 기준이 없음 |
| 화면 4개인데 명세는 3개 | 범위 절에 제외를 안 적어 구현자가 추가함 |
| 문서가 길기만 하고 결정이 없음 | 결정을 "추후 논의"로 미룸 |
| 사용자가 "이거 내가 준 거랑 다른데" | 원문을 고쳐 씀 |
