# verify-loop — 구현 → 검사 → 수정 → 재검사

이 스킬은 루프의 네 가지를 정한다. 누가 검사하는가, 검사가 무엇인가, 상태를 어디 두는가, 언제 나가는가.

## 누가 검사하는가

**만든 쪽이 아닌 쪽.** 문서는 doc-reviewer, 코드는 code-reviewer, 보안 관점은 security가 본다. 리뷰는 원장의 task이고 대상 task를 가리킨다. 검사하는 쪽은 산출물을 고치지 못한다.

검사하는 쪽이 볼 것은 셋이다.

1. **완료 기준** 각각이 산출물에서 확인되는가 (기계적: 테스트·빌드는 직접 실행 / 판단: 명세 항목 ↔ 산출물 대조)
2. **범위** 안에 있는가 — 소유 경로 밖 변경, 요청 밖 변경
3. 보고의 **증거 수준**이 실제와 맞는가 — "실행 검증"이라 적힌 것을 돌려 본다

보고서의 **"같이 고친 버그"** 절에 적힌 변경은 요청 밖 변경으로 잡지 않는다. 관련 있다고 판정한 버그는 함께 고칠 수 있다. 대신 셋을 본다. 관련성 판정이 타당한가(소유 경로 안인가, 완료 기준을 막았는가, 이번 변경이 드러냈는가), 수정에 재현과 증거가 있는가, 절에 적히지 않은 변경이 있는가. 절에 없는데 바뀐 것은 여전히 범위 이탈이다.

산출물이 문서라면 템플릿의 절이 다 있는지, 입력 문서의 항목이 빠짐없이 반영됐는지를 대조한다. 내용이 타당한지(과잉 설계, 불필요한 기술, 근거 부족)는 여기서 보지 않는다. 그것은 critic의 비평이고, 문서는 critic 비평과 doc-reviewer 판정을 둘 다 통과해야 끝난다.

보지 않을 것: 완료 기준에 없는 품질 취향, 다른 방식이었으면 하는 바람, 요청 밖 개선.

## 판정과 finding

판정(verdict)은 셋뿐이다.

| verdict | 뜻 | 다음 |
|---|---|---|
| `confirmed` | 완료 기준 전부 확인. 미해소 blocker 없음 | done |
| `needs-fix` | blocker 또는 major가 있다 | 리더가 재작업 task를 만든다 (`--target`, `--fixes`) |
| `inconclusive` | 환경 부재 등으로 판정 불가한 기준이 있다 | 리더가 대신 확인하거나 환경을 만드는 task를 추가한다 |

finding에는 ID(`<task>-F<n>`, 보안 검토는 `<task>-S<n>`), 심각도, 위치, 무엇이 기준과 어긋나는지, 재현 방법을 적는다. 리더가 대상 task에 기록한다.

| 심각도 | 기준 |
|---|---|
| `blocker` | 완료 기준 하나를 만족하지 못한다. 또는 소유 경로 밖을 바꿨다 |
| `major` | 완료 기준은 만족하나 요청한 동작이 특정 입력에서 깨진다. 또는 요청 밖 변경이 있다 |
| `minor` | 기준과 무관한 관찰. 재작업 대상이 아니다. 기록만 |

blocker와 major만 재작업을 일으킨다. minor를 고치라고 보내지 않는다. 사용자가 원하면 새 task다.

## 리뷰 파일

문서 템플릿 `review.md`로 쓴다.

## 상태는 파일에

회차, finding, 해소 여부는 리뷰 파일과 원장에 있다. 기억이나 대화에 두지 않는다. 재작업 브리프는 리뷰 파일 경로와 ID 목록을 넘기지, 지적을 요약해 옮기지 않는다.

## 재작업 규칙

- 재작업은 원래 만든 에이전트가 같은 워크트리에서 한다. **나열된 ID만** 고친다. 고치면서 발견한 다른 것은 보고에 적고 손대지 않는다.
- ID별로 무엇을 어떻게 고쳤는지 보고에 적는다. "전부 수정했습니다"는 보고가 아니다.
- round 2 검사는 round 1 인스턴스를 재개해서 한다. 이전 ID의 해소 여부를 먼저 적고, 새 finding은 **회귀**(고치다 깨진 것)와 **blocker**만 올린다. round 1에 못 본 major·minor를 round 2에 새로 올리지 않는다.
- finding에 반박이 있으면(명세가 그렇다, 기준이 틀렸다) 보고에 적는다. 판정이 안 되면 리더가 명세와 기준을 확인해 어느 쪽이 맞는지 정하고, 틀린 쪽(문서 또는 기준)을 고친다.

## 나가는 조건

| 조건 | 결과 |
|---|---|
| verdict confirmed | done |
| 재작업 2회 후에도 needs-fix | 같은 재작업을 다시 만들지 않는다. 리더가 원인을 찾는다 — 기준이 모호한지, 입력 문서가 틀렸는지, 결정이 빠졌는지. 원인이 문서면 그 문서를 critic 비평과 수정으로 돌려 고친 뒤 재작업을 다시 시작한다. 원인이 기준이면 기준을 고치고 리뷰를 다시 한다 |
| 같은 ID가 두 라운드 연속 open | 상위 결정이 비어 있는 것이다. 그 결정을 채우는 문서로 돌아간다(레벨 1이면 architect, 레벨 2면 그 문서를 쓴 에이전트). 채운 뒤 재작업 |
| 리더가 특정 ID를 넘기기로 함 | `waive`. 이유를 기록에 적고 run 보고서 "알고 넘긴 것"에 올린다. minor만 넘길 수 있다 |
| inconclusive | 리더가 확인 가능하면 대신 확인한다. 환경이 없어 확인할 수 없으면 환경을 만드는 task를 추가하고, 그것도 안 되면 미검증으로 run 보고서에 적는다 |

2회 안에 안 되면 기준이 모호하거나, 입력 문서가 틀렸거나, 결정이 빠진 것이다. 그 원인을 고치지 않고 같은 재작업을 반복하지 않는다.

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 라운드마다 새 지적이 나와 끝나지 않음 | round 2 이후 신규 major·minor 금지를 안 지킴 |
| 지적 5개 중 3개만 고치고 "완료" | ID별 보고를 요구하지 않음 |
| 검사하는 쪽이 코드를 고쳐 놓음 | 검사하는 쪽에 편집 도구가 있음 |
| "취향" 지적으로 재작업 | 심각도 기준을 완료 기준과 연결하지 않음 |
| 보고서만 읽고 confirmed | 실행 검증 항목을 직접 돌리지 않음 |
| 리뷰 라운드마다 처음부터 다시 읽음 | 새 인스턴스로 던짐. round 2는 재개 |
