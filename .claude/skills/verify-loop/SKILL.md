# verify-loop — 판정은 두 번까지, 고치는 것은 닫힐 때까지

이 스킬은 넷을 정한다. 누가 검사하는가, 검사가 무엇인가, 상태를 어디 두는가, 언제 나가는가.

판정 에이전트를 띄우는 것은 대상마다 **두 번까지**다. 1차는 첫 판 전체를 보고, 2차는 재작업 뒤 1차 지적이 해소됐는지만 본다. 3차는 없고 원장이 등록을 거부한다. 2차 뒤에 남은 지적은 리더가 같은 에이전트에게 되돌려 보내고 산출물을 직접 대조해 닫는다. 지적은 닫힐 때까지 고친다. 한 줄 고치고 판정, 또 한 줄 고치고 판정을 하지 않는다.

## 누가 검사하는가

**만든 쪽이 아닌 쪽.** 문서는 doc-reviewer, 코드는 code-reviewer, 보안 관점은 security가 본다. 리뷰는 원장의 task이고 대상 task를 가리킨다. 검사하는 쪽은 산출물을 고치지 못한다.

**코드는 기본으로 리뷰어를 붙이지 않는다.** 테스트·타입 검사·린트 통과가 코드의 완료 판정이고, 리더가 워크트리에서 직접 돌린다. code-reviewer는 사용자가 코드 리뷰를 요구했을 때, security 검토는 인증·시크릿·외부 호출·개인정보에 닿는 코드일 때만 붙는다.

**1차는 한 번에 전부 본다.** 새 지적을 낼 수 있는 것은 1차뿐이다. 검사 계획을 먼저 세우고(기준마다 무엇을 실행하고 무엇을 대조할지), 산출물을 처음부터 끝까지 읽고, 끝난 뒤 계획 대비 빠뜨린 항목이 없는지 확인한 다음 판정을 쓴다.

**2차는 해소 확인만 한다.** 같은 인스턴스가 이전 지적마다 resolved/open을 적는다. 새 지적은 고치다 깨진 것(회귀)과 blocker만 올린다. 1차에 못 본 major·minor를 2차에 새로 올리지 않는다.

검사하는 쪽이 볼 것은 셋이다.

1. **완료 기준** 각각이 산출물에서 확인되는가 (기계적: 테스트·빌드는 직접 실행 / 판단: 명세 항목 ↔ 산출물 대조)
2. **범위** 안에 있는가 — 소유 경로 밖 변경, 요청 밖 변경
3. 보고의 **증거 수준**이 실제와 맞는가 — "실행 검증"이라 적힌 것을 돌려 본다

보고서의 **"같이 고친 버그"** 절에 적힌 변경은 요청 밖 변경으로 잡지 않는다. 관련 있다고 판정한 버그는 함께 고칠 수 있다. 대신 셋을 본다. 관련성 판정이 타당한가(소유 경로 안인가, 완료 기준을 막았는가, 이번 변경이 드러냈는가), 수정에 재현과 증거가 있는가, 절에 적히지 않은 변경이 있는가. 절에 없는데 바뀐 것은 여전히 범위 이탈이다.

보고서의 **"명세에 없어 내가 정한 것"**에 레벨 2 세부(필드, 문구, 엣지 케이스, 수치)가 있는 것은 정상이다. 구현 중 문서를 고치지 않는 것이 규칙이고, run 끝의 문서 정합 task가 옮긴다. 레벨 1(구조)이 있으면 범위 이탈이다.

산출물이 문서라면 템플릿의 절이 다 있는지, 입력 문서의 항목이 빠짐없이 반영됐는지를 대조한다. 내용이 타당한지(과잉 설계, 불필요한 기술, 근거 부족)는 여기서 보지 않는다. 그것은 critic의 비평이다.

보지 않을 것: 완료 기준에 없는 품질 취향, 다른 방식이었으면 하는 바람, 요청 밖 개선.

## 판정과 finding

판정(verdict)은 셋뿐이다.

| verdict | 뜻 | 다음 |
|---|---|---|
| `confirmed` | 완료 기준 전부 확인. blocker·major 없음 | 끝 |
| `needs-fix` | blocker 또는 major가 있다 | 1차면 리더가 재작업 task를 만든다 (`--target`, `--fixes`). 2차면 리더가 남은 것을 되돌려 보내고 직접 닫는다 |
| `inconclusive` | 환경 부재 등으로 판정 불가한 기준이 있다 | 리더가 대신 확인하거나 환경을 만드는 task를 추가한다 |

finding에는 번호(`<task>-F<n>`, 보안 검토는 `<task>-S<n>`), 심각도, 위치, 무엇이 기준과 어긋나는지, 재현 방법을 적는다. 리더가 대상 task에 기록한다. 번호는 `_tasks/` 안에서 서로 가리키는 용도다. 사용자에게 말할 때와 `docs/`에는 번호 대신 내용을 쓴다.

| 심각도 | 기준 |
|---|---|
| `blocker` | 완료 기준 하나를 만족하지 못한다. 또는 소유 경로 밖을 바꿨다 |
| `major` | 완료 기준은 만족하나 요청한 동작이 특정 입력에서 깨진다. 또는 요청 밖 변경이 있다. 또는 같은 규칙을 다른 문서에서 옮겨 적어 정본이 둘이 됐다 |
| `minor` | 기준과 무관한 관찰. **형식 지적은 전부 여기다** — 링크 없는 문서 언급, 깨진 링크, 문체, 제목 형태, 번호 표기 위치, 볼드·번호 개수, 템플릿 안내문 잔재. 재작업 대상이 아니다. 기록만 |

blocker와 major만 재작업을 일으킨다. minor는 `--fixes`에 들어가지 않는다(원장이 거부한다). run 끝의 문서 정합 task에서 몰아 고치거나 버린다.

`docs/`에 작업 기록(task 번호, 지적 번호, 라운드, 에이전트 이름, `_tasks/` 경로)이 남은 것은 리뷰어가 잡을 일이 아니다. `docs-lint.py`가 `set done`에서 자동으로 막고, 리더가 만든 에이전트에게 바로 지우게 한다.

## 리뷰 파일

문서 템플릿 `review.md`로 쓴다. 2차는 같은 템플릿의 "2차 확인" 절을 채운다.

## 상태는 파일에

finding과 해소 여부는 리뷰 파일과 원장에 있다. 기억이나 대화에 두지 않는다. 재작업 브리프는 리뷰 파일 경로와 고칠 지적의 번호를 넘기지, 지적을 요약해 옮기지 않는다.

## 재작업 규칙

- 재작업은 원래 만든 에이전트가 같은 워크트리에서 한다. 원래 인스턴스를 `SendMessage`로 재개한다. **나열된 지적만** 고친다. 고치면서 발견한 다른 것은 보고에 적고 손대지 않는다.
- 판정이 여럿(비평, 문서 리뷰, 보안 검토)이면 리더는 전부 끝난 뒤 blocker·major를 모아 재작업 하나에 넘긴다. 판정마다 재작업을 따로 만들지 않는다.
- 지적마다 무엇을 어떻게 고쳤는지, 어디를 보면 확인되는지 보고에 적는다. "전부 수정했습니다"는 보고가 아니다.
- 지적에 반박이 있으면(명세가 그렇다, 기준이 틀렸다) 보고에 적는다. 리더가 명세와 기준을 확인해 어느 쪽이 맞는지 정한다.
- 재작업이 끝나면 1차 판정 인스턴스가 2차 확인을 한다. 2차 뒤에도 남은 지적은 리더가 같은 에이전트에게 되돌려 보내고, 고쳐진 것을 리뷰 파일과 산출물을 대조해 직접 확인한 뒤 `finding resolve`한다. 닫힐 때까지 반복한다. 판정 에이전트는 다시 띄우지 않는다.

## 나가는 조건

| 조건 | 결과 |
|---|---|
| verdict confirmed | 끝 |
| 1차 needs-fix → 재작업 → 2차 confirmed | 끝 |
| 2차 뒤에도 열린 지적 | 리더가 되돌려 보내고 직접 대조해 닫는다. 판정은 더 만들지 않는다 |
| 반박이 맞다(명세가 그렇다, 기준이 틀렸다) | 리더가 확인한 뒤 `finding waive`(기각). 이유를 적고 run 보고서 "결정 경위"에 내용으로 적는다. 이것이 고치지 않고 닫는 유일한 경로다 |
| 같은 지적이 두 번 되돌려 보내도 안 닫힘 | 상위 결정이 비어 있는 것이다. 그 결정을 채우는 문서에 재작업 task(레벨 1이면 architect, 레벨 2면 그 문서를 쓴 에이전트). 그 문서가 고쳐진 뒤 원래 지적을 다시 고친다 |
| inconclusive | 리더가 확인 가능하면 대신 확인한다. 환경이 없어 확인할 수 없으면 환경을 만드는 task를 추가하고, 그것도 안 되면 미검증으로 run 보고서에 적는다 |

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 한 줄 고치고 다시 판정, 또 한 줄 고치고 다시 판정 | 판정 두 번 상한을 안 지킴. 2차 뒤는 리더가 직접 닫는다 |
| 2차에서 새 지적이 쏟아짐 | 1차가 전체를 안 봄. 1차는 검사 계획을 다 지나고 판정한다 |
| 안 고쳐진 지적을 "알고 넘김"으로 닫음 | 기각은 반박이 맞을 때만. 결함은 닫힐 때까지 고친다 |
| 지적 5개 중 3개만 고치고 "완료" | 지적별 보고를 요구하지 않음 |
| 검사하는 쪽이 코드를 고쳐 놓음 | 검사하는 쪽에 편집 도구가 있음 |
| "취향"·형식 지적으로 재작업 | 심각도를 완료 기준과 연결하지 않음. 형식은 minor |
| 보고서만 읽고 confirmed | 실행 검증 항목을 직접 돌리지 않음 |
| 문서 하나에 판정 17번 | 판정마다 재작업, 재작업마다 재판정. 판정은 두 번까지 |
| 코드 task 하나에 리뷰·보안·재작업·재리뷰 | 테스트 통과가 판정인데 리뷰어를 기본으로 붙임 |
| 사용자 보고에 "T1-F3 해소" | 번호는 `_tasks/` 안에서만. 사용자에게는 내용으로 |
