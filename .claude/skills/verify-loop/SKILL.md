# verify-loop — 한 번 검사하고, 한 번 고치고, 닫는다

이 스킬은 넷을 정한다. 누가 검사하는가, 검사가 무엇인가, 상태를 어디 두는가, 언제 나가는가. 루프는 두 바퀴가 없다. **판정 한 번 → 재작업 한 번 → 리더가 닫는다.** 원장이 두 번째 판정과 두 번째 재작업의 등록을 거부한다.

## 누가 검사하는가

**만든 쪽이 아닌 쪽.** 문서는 doc-reviewer, 코드는 code-reviewer, 보안 관점은 security가 본다. 리뷰는 원장의 task이고 대상 task를 가리킨다. 검사하는 쪽은 산출물을 고치지 못한다.

**코드는 기본으로 리뷰어를 붙이지 않는다.** 테스트·타입 검사·린트 통과가 코드의 완료 판정이고, 리더가 워크트리에서 직접 돌린다. code-reviewer는 사용자가 코드 리뷰를 요구했을 때, security 검토는 인증·시크릿·외부 호출·개인정보에 닿는 코드일 때만 한 번 붙는다.

**한 번에 전부 본다.** 검사는 대상마다 한 번이다. 다음 라운드가 없으므로 이번에 못 본 것은 영영 못 본다. 검사 계획을 먼저 세우고(기준마다 무엇을 실행하고 무엇을 대조할지), 산출물을 처음부터 끝까지 읽고, 끝난 뒤 계획 대비 빠뜨린 항목이 없는지 확인한 다음 판정을 쓴다.

검사하는 쪽이 볼 것은 셋이다.

1. **완료 기준** 각각이 산출물에서 확인되는가 (기계적: 테스트·빌드는 직접 실행 / 판단: 명세 항목 ↔ 산출물 대조)
2. **범위** 안에 있는가 — 소유 경로 밖 변경, 요청 밖 변경
3. 보고의 **증거 수준**이 실제와 맞는가 — "실행 검증"이라 적힌 것을 돌려 본다

보고서의 **"같이 고친 버그"** 절에 적힌 변경은 요청 밖 변경으로 잡지 않는다. 관련 있다고 판정한 버그는 함께 고칠 수 있다. 대신 셋을 본다. 관련성 판정이 타당한가(소유 경로 안인가, 완료 기준을 막았는가, 이번 변경이 드러냈는가), 수정에 재현과 증거가 있는가, 절에 적히지 않은 변경이 있는가. 절에 없는데 바뀐 것은 여전히 범위 이탈이다.

보고서의 **"명세에 없어 내가 정한 것"**에 레벨 2 세부(필드, 문구, 엣지 케이스, 수치)가 있는 것은 정상이다. 구현 중 문서를 고치지 않는 것이 규칙이고, run 끝의 문서 정합 task가 옮긴다. 레벨 1(구조)이 있으면 범위 이탈이다.

산출물이 문서라면 템플릿의 절이 다 있는지, 입력 문서의 항목이 빠짐없이 반영됐는지를 대조한다. 내용이 타당한지(과잉 설계, 불필요한 기술, 근거 부족)는 여기서 보지 않는다. 그것은 critic의 비평이다.

보지 않을 것: 완료 기준에 없는 품질 취향, 다른 방식이었으면 하는 바람, 요청 밖 개선.

## 판정과 finding

판정(verdict)은 셋뿐이다.

| verdict | 뜻 | 다음 |
|---|---|---|
| `confirmed` | 완료 기준 전부 확인. blocker·major 없음 | 끝 |
| `needs-fix` | blocker 또는 major가 있다 | 리더가 재작업 task 하나를 만든다 (`--target`, `--fixes`) |
| `inconclusive` | 환경 부재 등으로 판정 불가한 기준이 있다 | 리더가 대신 확인하거나 환경을 만드는 task를 추가한다 |

finding에는 ID(`<task>-F<n>`, 보안 검토는 `<task>-S<n>`), 심각도, 위치, 무엇이 기준과 어긋나는지, 재현 방법을 적는다. 리더가 대상 task에 기록한다.

| 심각도 | 기준 |
|---|---|
| `blocker` | 완료 기준 하나를 만족하지 못한다. 또는 소유 경로 밖을 바꿨다 |
| `major` | 완료 기준은 만족하나 요청한 동작이 특정 입력에서 깨진다. 또는 요청 밖 변경이 있다. 또는 같은 규칙을 다른 문서에서 옮겨 적어 정본이 둘이 됐다 |
| `minor` | 기준과 무관한 관찰. **형식 지적은 전부 여기다** — 링크 없는 문서 언급, 깨진 링크, 문체, 제목 형태, ID 표기 위치, 볼드·번호 개수, 템플릿 안내문 잔재. 재작업 대상이 아니다. 기록만 |

blocker와 major만 재작업을 일으킨다. minor는 `--fixes`에 들어가지 않는다(원장이 거부한다). run 끝의 문서 정합 task에서 몰아 고치거나 버린다.

`docs/`에 작업 기록(task ID, finding 번호, 라운드, 에이전트 이름, `_tasks/` 경로)이 남은 것은 리뷰어가 잡을 일이 아니다. `docs-lint.py`가 `set done`에서 자동으로 막고, 리더가 만든 에이전트에게 바로 지우게 한다.

## 리뷰 파일

문서 템플릿 `review.md`로 쓴다.

## 상태는 파일에

finding과 해소 여부는 리뷰 파일과 원장에 있다. 기억이나 대화에 두지 않는다. 재작업 브리프는 리뷰 파일 경로와 ID 목록을 넘기지, 지적을 요약해 옮기지 않는다.

## 재작업 규칙

- 재작업은 원래 만든 에이전트가 같은 워크트리에서 한다. 원래 인스턴스를 `SendMessage`로 재개한다. **나열된 ID만** 고친다. 고치면서 발견한 다른 것은 보고에 적고 손대지 않는다.
- 판정이 여럿(비평, 문서 리뷰, 보안 검토)이면 리더는 전부 끝난 뒤 blocker·major를 모아 재작업 하나에 넘긴다. 판정마다 재작업을 따로 만들지 않는다.
- ID별로 무엇을 어떻게 고쳤는지, 어디를 보면 확인되는지 보고에 적는다. "전부 수정했습니다"는 보고가 아니다.
- finding에 반박이 있으면(명세가 그렇다, 기준이 틀렸다) 보고에 적는다. 리더가 명세와 기준을 확인해 어느 쪽이 맞는지 정한다.
- **두 번째 검사는 없다.** 재작업이 끝나면 리더가 보고서의 ID별 설명을 산출물과 대조해 `finding resolve`한다. 설명이 없거나 산출물이 설명과 다르면 그 ID는 `waive`하고 run 보고서 "문제가 있는 것"에 적는다.

## 나가는 조건

| 조건 | 결과 |
|---|---|
| verdict confirmed | 끝 |
| needs-fix → 재작업 완료, 리더가 ID별 확인 | resolve된 것은 닫힘. 안 된 것은 waive + run 보고서 "문제가 있는 것" |
| 재작업 보고에 반박 | 리더가 명세·기준을 확인. 기준이 틀렸으면 waive(이유 기록). 산출물이 틀렸으면 waive + run 보고서. 사용자가 원하면 새 task |
| finding의 원인이 상위 결정 공백 | 원래 finding은 waive. 그 결정을 채우는 문서에 재작업 task(레벨 1이면 architect, 레벨 2면 그 문서를 쓴 에이전트). run 보고서에 그 task를 가리켜 적는다 |
| inconclusive | 리더가 확인 가능하면 대신 확인한다. 환경이 없어 확인할 수 없으면 환경을 만드는 task를 추가하고, 그것도 안 되면 미검증으로 run 보고서에 적는다 |

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 한 줄 고치고 다시 검사, 또 한 줄 고치고 다시 검사 | 검사가 전체를 한 번에 안 봄. 검사 계획 없이 읽은 데까지만 판정함 |
| 지적 5개 중 3개만 고치고 "완료" | ID별 보고를 요구하지 않음 |
| 검사하는 쪽이 코드를 고쳐 놓음 | 검사하는 쪽에 편집 도구가 있음 |
| "취향"·형식 지적으로 재작업 | 심각도를 완료 기준과 연결하지 않음. 형식은 minor |
| 보고서만 읽고 confirmed | 실행 검증 항목을 직접 돌리지 않음 |
| 문서 하나에 판정 17번 | 판정마다 재작업, 재작업마다 재판정. 판정은 한 번, 재작업도 한 번 |
| 코드 task 하나에 리뷰·보안·재작업·재리뷰 | 테스트 통과가 판정인데 리뷰어를 기본으로 붙임 |
