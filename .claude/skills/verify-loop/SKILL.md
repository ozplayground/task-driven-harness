# verify-loop — 구현 → 검사 → 수정 → 재검사

이 스킬은 루프의 네 가지를 정한다. 누가 검사하는가, 검사가 무엇인가, 상태를 어디 두는가, 언제 나가는가.

## 누가 검사하는가

**만든 쪽이 아닌 쪽.** 만든 쪽은 자기 보고를 쓰고, 검사하는 쪽은 별개 인스턴스로 산출물을 본다. 검사하는 쪽은 산출물을 고치지 못한다.

검사하는 쪽이 볼 것은 셋이다.

1. **완료 기준** 각각이 산출물에서 확인되는가 (기계적: 테스트·빌드는 직접 실행 / 판단: 명세 항목 ↔ 산출물 대조)
2. **범위** 안에 있는가 — 소유 경로 밖 변경, 요청 밖 변경
3. 보고의 **증거 수준**이 실제와 맞는가 — "실행 검증"이라 적힌 것을 돌려 본다

보고서의 **"같이 고친 버그"** 절에 적힌 변경은 요청 밖 변경으로 잡지 않는다. 관련 있다고 판정한 버그는 함께 고칠 수 있다. 대신 셋을 본다. 관련성 판정이 타당한가(소유 경로 안인가, 완료 기준을 막았는가, 이번 변경이 드러냈는가), 수정에 재현과 증거가 있는가, 절에 적히지 않은 변경이 있는가. 절에 없는데 바뀐 것은 여전히 범위 이탈이다.

보지 않을 것: 완료 기준에 없는 품질 취향, 다른 방식이었으면 하는 바람, 요청 밖 개선.

## 판정과 finding

판정(verdict)은 셋뿐이다.

| verdict | 뜻 | 다음 |
|---|---|---|
| `confirmed` | 완료 기준 전부 확인. 미해소 blocker 없음 | done |
| `needs-fix` | blocker 또는 major가 있다 | rework |
| `inconclusive` | 환경 부재 등으로 판정 불가한 기준이 있다 | 대신 확인하거나 사용자에게 |

finding에는 ID(`<task>-F<n>`), 심각도, 위치, 무엇이 기준과 어긋나는지, 재현 방법을 적는다.

| 심각도 | 기준 |
|---|---|
| `blocker` | 완료 기준 하나를 만족하지 못한다. 또는 소유 경로 밖을 바꿨다 |
| `major` | 완료 기준은 만족하나 요청한 동작이 특정 입력에서 깨진다. 또는 요청 밖 변경이 있다 |
| `minor` | 기준과 무관한 관찰. 재작업 대상이 아니다. 기록만 |

blocker와 major만 재작업을 일으킨다. minor를 고치라고 보내지 않는다. 사용자가 원하면 새 task다.

## 리뷰 파일 형식

```markdown
# <id> 리뷰 round <n>

verdict: needs-fix

## 완료 기준 확인
| 기준 | 결과 | 확인 방법 |
|---|---|---|
| tests/api/orders.test.ts 통과 | 통과 | 직접 실행, 12 passed |
| GET /orders 가 T1 규격 응답 | 불일치 | curl 결과 `total` 필드 없음. T1 규격 §2.1 |

## 범위
- 소유 경로 밖 변경: 없음
- 요청 밖 변경: src/utils/date.ts 포맷 함수 수정 (요청에 없음)

## findings
| id | 심각도 | 위치 | 내용 | 재현 |
|---|---|---|---|---|
| T2-F1 | blocker | src/api/orders/handler.ts:33 | 응답에 total 누락. T1 §2.1 위반 | curl localhost:3000/orders |
| T2-F2 | major | src/utils/date.ts | 요청 밖 수정. 되돌리거나 사용자 확인 | git diff |
| T2-F3 | minor | src/api/orders/schema.ts:10 | 주석과 타입 불일치 | - |

## 이전 라운드 finding (round 2 이상)
| id | 상태 | 확인 |
|---|---|---|
| T2-F1 | resolved | total 필드 확인, curl 출력 |
| T2-F2 | open | 여전히 수정돼 있음 |
```

## 상태는 파일에

회차, finding, 해소 여부는 리뷰 파일과 진행 기록에 있다. 기억이나 대화에 두지 않는다. 재작업 브리프는 리뷰 파일 경로와 ID 목록을 넘기지, 지적을 요약해 옮기지 않는다.

## 재작업 규칙

- 고치는 쪽은 **나열된 ID만** 고친다. 고치면서 발견한 다른 것은 보고에 적고 손대지 않는다.
- ID별로 무엇을 어떻게 고쳤는지 보고에 적는다. "전부 수정했습니다"는 보고가 아니다.
- 검사하는 쪽은 round 2부터 이전 ID의 해소 여부를 먼저 적고, 새 finding은 **회귀**(고치다 깨진 것)와 **blocker**만 올린다. round 1에 못 본 major·minor를 round 2에 새로 올리지 않는다.
- finding에 반박이 있으면(명세가 그렇다, 기준이 틀렸다) 보고에 적는다. 판정이 안 되면 사용자에게 올린다.

## 나가는 조건

| 조건 | 결과 |
|---|---|
| verdict confirmed | done |
| 재작업 2회 후에도 needs-fix | blocked. 미해소 ID와 함께 사용자에게 |
| 같은 ID가 두 라운드 연속 open | 대개 상위 결정이 비어 있다. 다시 돌리지 말고 사용자에게 |
| 사용자가 특정 ID를 넘기라고 함 | `waive`. 이유를 기록에 |
| inconclusive | 확인 가능하면 대신 확인. 아니면 미검증으로 명시하고 사용자에게 |

2회 안에 안 되면 기준이 모호하거나, 입력 문서가 틀렸거나, 결정이 빠진 것이다.

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 라운드마다 새 지적이 나와 끝나지 않음 | round 2 이후 신규 major·minor 금지를 안 지킴 |
| 지적 5개 중 3개만 고치고 "완료" | ID별 보고를 요구하지 않음 |
| 검사하는 쪽이 코드를 고쳐 놓음 | 검사하는 쪽에 편집 도구가 있음 |
| "취향" 지적으로 재작업 | 심각도 기준을 완료 기준과 연결하지 않음 |
| 보고서만 읽고 confirmed | 실행 검증 항목을 직접 돌리지 않음 |
