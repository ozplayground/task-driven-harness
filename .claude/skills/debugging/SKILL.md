# debugging — 원인을 알기 전에 고치지 않는다

## 절차

### 1. 재현한다

- 증상을 **재현하는 절차**를 먼저 만든다. 명령 하나, 테스트 하나, 요청 하나.
- 재현이 간헐적이면 조건(순서, 타이밍, 데이터)을 좁힌다. 좁혀지기 전에는 고치지 않는다.
- 가능하면 재현을 **실패하는 테스트**로 만든다. 이 테스트가 통과하는 것이 완료 기준이 된다.

### 2. 원인을 찾는다

- 증상이 나는 곳에서 **거꾸로** 따라간다. 잘못된 값이 어디서 만들어졌는가. 그 입력은 어디서 왔는가.
- 가설을 세우면 **확인**한다. 로그, 디버거, 값 출력. 확인 없이 다음 가설로 넘어가지 않는다.
- 최근 변경을 본다. `git log`, `git blame`. 어제까지 되던 것이면 그 사이 변경 안에 있다.
- 모르는 부분은 "이 값은 어디서 결정되는가"부터 확인한다.
- **원인을 한 문장으로 쓸 수 있을 때** 3단계로 간다. "X가 Y일 때 Z가 W를 가정해서". 못 쓰면 아직 모르는 것이다.

### 3. 고친다

- 원인을 고친다. 증상을 고치지 않는다. 증상 자리에 null 체크를 넣지 않는다.
- **가장 작은 변경.** 고치는 김에 주변을 정리하지 않는다.
- 소유 경로 밖에 원인이 있으면 고치지 않고 보고한다. 위치와 원인과 제안.

### 4. 증명한다

- 1단계의 재현 절차(테스트)가 **통과**한다. 이것이 "수정됨"의 유일한 증거다. 코드를 고쳤다는 것은 증거가 아니다.
- 전체 테스트가 그대로 통과한다.
- 보고에 적는다. 증상, 재현, 원인(한 문장), 수정, 증명.

## 멈춰야 하는 신호

이 중 하나가 보이면 그 자리에서 멈추고 2단계로 돌아간다.

- "일단 이렇게 해 보고 되는지 보자"
- "왜 되는지는 모르겠는데 됩니다"
- `try/catch`로 에러가 사라지게 함
- 테스트를 조건에 맞게 고쳐서 통과시킴 (결함은 남고 방어선만 사라진다)
- 재시도·타임아웃 늘리기로 간헐 오류를 감춤
- 같은 접근을 세 번 바꿔 시도함 (가설이 틀렸다. 원인으로 돌아간다)

## 보고 형식 (완료 기준 표 위에)

```
증상: GET /orders 가 status=paid 필터에서 빈 목록
재현: tests/api/orders.test.ts "filters by status" (수정 전 실패)
원인: 쿼리 빌더가 status 를 문자열이 아닌 enum 인덱스로 비교 (src/api/orders/query.ts:41)
수정: 비교 전 enum → 문자열 변환. 1줄
증명: 해당 테스트 통과, 전체 88건 통과 (실행 검증)
```

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 고쳤는데 다른 입력에서 재발 | 증상 자리를 덮음. 원인은 상류 |
| 수정 diff가 30줄인데 버그는 1줄 | 고치면서 정리함 |
| "수정 완료"인데 다시 재현됨 | 재현 테스트 없이 코드만 고침 |
| 테스트를 바꿔서 통과 | 테스트가 맞고 코드가 틀린 것을 거꾸로 판단 |
| 세 시간째 가설 바꾸는 중 | 확인 없이 가설만 교체. 값을 실제로 출력할 것 |
