# 주제 규제·심사 요건

| 항목 | 내용 |
|---|---|
| 적용 대상 | 제품 이름 |
| 참고 문서 | 이 문서가 근거로 삼은 문서. 링크로 적는다. `[요구사항 정의서](../prd/orders.md)` |

이 문서는 어떤 데이터가 어떤 규제나 심사의 대상이고, 그래서 설계에서 무엇을 반드시 지켜야 하는지 정한다. 데이터 모델과 화면 설계보다 먼저 있어야 한다. 보관 기간과 삭제 방식이 데이터 모델을 바꾸기 때문이다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 대상 데이터

이 제품이 다루는 데이터 중 규제 대상이 될 수 있는 것을 나열한다. 데이터마다 분류(개인정보, 민감정보, 결제정보 등)와 어디서 생기는지 적는다.

작성 예:

| 데이터 | 분류 | 어디서 생기나 |
|---|---|---|
| 주문자 이름, 연락처 | 개인정보 | 쇼핑몰에서 주문 생성 시 |
| 결제 수단 마지막 4자리 | 결제정보 | 결제 대행사 응답 |

## 2. 적용되는 규제와 요건

어떤 법령, 스토어 정책, 회사 규정이 적용되는지와 왜 적용되는지, 원문이 어디 있는지 적는다.

작성 예:

| 규제·요건 | 적용 이유 | 원문 위치 |
|---|---|---|
| 개인정보보호법 | 주문자 이름과 연락처를 저장한다 | 법령 제21조(파기) |
| 전자상거래법 | 주문 기록 보관 의무 | 시행령 제6조 |

## 3. 지켜야 할 것

요건을 하나씩 번호(C-nn)를 붙여 적는다. 요건마다 어떤 종류인지(동의·고지, 보관·삭제·이전, 접근 통제), 설계에서 무엇을 강제하는지 적는다. 설계 문서와 데이터 모델은 이 번호를 가리킨다.

작성 예:

| 번호 | 요건 | 종류 | 설계에 강제되는 것 |
|---|---|---|---|
| C-01 | 주문자 연락처는 주문 완료 90일 뒤 지운다 | 보관·삭제 | E-Order.orderer_phone을 배치로 null 처리. 데이터 모델 §5 |
| C-02 | 주문 기록은 5년 보관한다 | 보관 | 주문 삭제 배치는 연락처만 지우고 주문은 남긴다 |
| C-03 | 연락처는 담당자 이상만 볼 수 있고 화면에서 마스킹한다 | 접근 통제 | REQ-01 SCR-02 권한 표, FSD 4.6 |
| C-04 | 연락처를 로그에 남기지 않는다 | 접근 통제 | 코드 규칙 로깅 절 |

## 4. 확인 방법

각 요건이 지켜졌는지 어떻게 확인하는지 적는다. 테스트, 코드 리뷰, 로그 검사.

작성 예:

| 요건 | 확인 방법 |
|---|---|
| C-01 | 90일 지난 주문의 연락처가 null인지 확인하는 테스트 TC-31 |
| C-04 | 로그 전체에서 전화번호 형식 문자열 검색 결과 0건 |
