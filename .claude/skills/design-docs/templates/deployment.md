# 배포 절차

| 항목 | 내용 |
|---|---|
| 대상 | 제품 이름 |
| 참고 문서 | 이 문서가 근거로 삼은 문서. 링크로 적는다. `[요구사항 정의서](../prd/orders.md)` |

이 문서는 어디에 어떻게 올리고, 잘못됐을 때 어떻게 되돌리는지 정한다. 처음 보는 사람이 이 문서만 보고 배포할 수 있어야 한다. 시크릿 값은 절대 적지 않고 이름과 보관 위치만 적는다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 환경

환경마다 용도, 실행 단위가 어디서 도는지, 인프라와 버전을 적는다. 아키텍처 문서의 배포 절과 같아야 한다.

작성 예:

| 환경 | 용도 | 실행 단위 | 인프라 |
|---|---|---|---|
| 스테이징 | 배포 전 확인 | api, worker 컨테이너 2개, web 컨테이너 1개 | 단일 VM, Docker Compose, PostgreSQL 18 |
| 운영 | 실제 서비스 | 같음 | 단일 VM, 일 1회 DB 백업 |

## 2. 인프라 구성

인프라 정의 파일이 어디 있고 무엇을 만드는지, 구성 요소가 어떻게 연결되는지 적는다.

작성 예:

> `deploy/compose.prod.yaml`이 api, worker, web, postgres 네 컨테이너를 정의한다. 외부에서는 web의 443만 열린다. api는 web에서만, postgres는 api와 worker에서만 접근한다.

## 3. 배포 순서

명령 단위로 순서대로 적는다. 각 단계에서 무엇을 확인해야 다음으로 가는지 쓴다.

작성 예:

1. 태그를 만든다. `git tag v1.4.0 && git push --tags`
2. 이미지를 빌드해 올린다. `make build-push TAG=v1.4.0`
3. 스테이징에 올린다. `make deploy ENV=staging TAG=v1.4.0`
4. 스테이징에서 확인한다. `/api/v1/health`가 200이고, 로그인 후 주문 목록이 보인다.
5. 운영에 올린다. `make deploy ENV=prod TAG=v1.4.0`
6. 운영에서 4번을 반복한다.

## 4. 데이터베이스 변경

스키마 변경이 있을 때의 순서를 적는다. 배포 전에 하는지 후에 하는지, 되돌릴 수 있는지.

작성 예:

> 마이그레이션은 api 컨테이너를 올리기 전에 `make migrate ENV=prod`로 먼저 적용한다. 열 삭제가 포함된 마이그레이션은 이전 배포에서 쓰기를 멈춘 뒤 다음 배포에서 적용한다(데이터 모델 §6).

## 5. 되돌리기

어떤 상황이면 되돌리는지, 되돌리는 명령, 되돌린 뒤 무엇을 확인하는지 적는다.

작성 예:

> 조건: 배포 후 10분 안에 5xx 비율이 1%를 넘거나 로그인이 안 되면 되돌린다.
> 절차: `make deploy ENV=prod TAG=<이전 태그>`. 마이그레이션이 있었다면 `make migrate-down ENV=prod` 먼저.
> 확인: `/api/v1/health` 200, 로그인 후 주문 목록.

## 6. 시크릿 목록

시크릿의 이름, 누가 쓰는지, 어디에 보관하는지 적는다. 값은 적지 않는다.

작성 예:

| 이름 | 쓰는 곳 | 보관 |
|---|---|---|
| DB 접속 URL | api, worker | VM의 `/etc/orders/database.url` (0600) |
| JWT 서명 키 | api | `/etc/orders/jwt.key` |
| 결제 대행사 API 키 | worker | `/etc/orders/payment.key` |
