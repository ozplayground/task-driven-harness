# REQ-00 요구사항 이름 기능 명세서 (FSD)

| 항목 | 내용 |
|---|---|
| 상세화하는 요구사항 | REQ-00 (PRD 경로) |
| 참고 문서 | 이 문서가 근거로 삼은 문서. 링크로 적는다. `[요구사항 정의서](../prd/orders.md)` |

이 문서는 요구사항 하나가 정확히 어떻게 동작하는지를 정한다. 구현하는 사람이 화면, 문구, 기본값, 규칙을 스스로 정해야 하는 곳이 없어야 한다. 요구사항을 기능(FN-nn) 단위로 나누고, 기능마다 화면, 흐름, 규칙, 검증, 권한, 메시지, 데이터, 연동, 예외를 쓴다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 요구사항 인용

PRD에 적힌 요구사항의 정의와 인수 조건을 그대로 옮겨 적는다. 이 인용이 이 문서의 범위다. 여기서 벗어나지 않고, 여기 있는 것을 빠뜨리지 않는다.

작성 예:

> **REQ-02 결제 실패 건 처리** — 담당자가 결제 실패 주문을 확인하고 재시도를 요청한다.
> 인수 조건: (1) 결제 실패 주문만 모아 볼 수 있다. (2) 재시도를 요청하면 주문 상태가 '결제 대기'로 바뀌고 결과가 갱신된다.

## 2. 기능 목록

요구사항을 기능으로 나눈다. 기능 하나는 사용자가 한 번의 목적으로 끝까지 하는 동작 묶음이다. 기능마다 번호, 이름, 한 줄 정의, 어느 인수 조건을 받는지 적는다. 인수 조건마다 받는 기능이 있어야 한다.

작성 예:

| 번호 | 이름 | 정의 | 받는 인수 조건 |
|---|---|---|---|
| FN-01 | 결제 실패 목록 | 결제 실패 상태인 주문만 모아 보여 준다 | (1) |
| FN-02 | 재시도 요청 | 결제 실패 주문의 결제를 다시 시도하도록 요청한다 | (2) |

## 3. 사용 역할과 선행 조건

이 요구사항을 쓰는 역할과, 쓰기 전에 갖춰져 있어야 하는 것을 적는다.

작성 예:

> 역할: 담당자, 관리자. 조회 역할은 목록만 볼 수 있고 재시도는 할 수 없다.
> 선행 조건: 로그인돼 있어야 한다. 결제 대행사 연동(REQ-05)이 설정돼 있어야 한다.

## 4. 기능 상세

기능마다 아래 절을 모두 쓴다. 해당하는 내용이 없는 절은 지우지 말고 "해당 없음"과 이유를 적는다.

### FN-01 결제 실패 목록

#### 4.1 화면

이 기능이 쓰는 화면을 적는다. 화면 번호(SCR-nn)와 이름은 UX 설계 문서의 화면 목록에서 가져온다. 화면마다 어디서 들어오는지, 어디로 나가는지, 누가 볼 수 있는지. 그 다음 화면마다 구성 요소를 모두 적는다. 요소마다 번호(SCR-nn-Enn), 종류, 라벨, 기본값, 필수 여부, 입력 제약, 언제 보이는지, 눌렀을 때 무슨 일이 생기는지. 목록 화면이면 컬럼, 정렬, 필터, 검색, 페이지 크기를 적는다. 로딩 중, 비어 있을 때, 오류일 때, 권한이 없을 때 무엇이 보이는지도 적는다.

작성 예:

**SCR-01 결제 실패 목록** — 진입: 좌측 메뉴 '결제 실패'. 이동: 행을 누르면 주문 상세(REQ-01 SCR-02). 권한: 담당자, 관리자, 조회.

| 요소 | 종류 | 라벨 | 기본값 | 필수 | 제약 | 표시 조건 | 동작 |
|---|---|---|---|---|---|---|---|
| SCR-01-E01 | 기간 선택 | 실패 일시 | 최근 7일 | 아니오 | 최대 90일 | 항상 | 바꾸면 목록을 다시 조회한다 |
| SCR-01-E02 | 검색창 | 주문자 이름 | 비어 있음 | 아니오 | 50자 | 항상 | 입력을 멈춘 뒤 300ms에 조회한다 |
| SCR-01-E03 | 버튼 | 재시도 요청 | | | | 담당자, 관리자에게만 | FN-02로 이어진다 |

목록: 컬럼은 주문번호, 주문자, 금액, 실패 일시, 실패 사유. 실패 일시 내림차순. 한 페이지 20건.

| 상태 | 보이는 것 |
|---|---|
| 로딩 | 표 자리에 스켈레톤 |
| 비어 있음 | "조건에 맞는 결제 실패 주문이 없습니다." |
| 오류 | MSG-01과 다시 시도 버튼 |
| 권한 없음 | 메뉴 자체가 보이지 않는다 |

#### 4.2 흐름

정상 흐름을 단계로 쓰고, 갈라지는 경우(대안 흐름)와 실패하는 경우(예외 흐름)를 따로 쓴다. 상태가 있으면 상태 전이를 표로 적는다.

작성 예:

> 정상: (1) 담당자가 메뉴를 누른다 → (2) 최근 7일 결제 실패 주문을 조회한다 → (3) 목록을 보여 준다.
> 예외: (2)에서 조회가 실패하면 MSG-01을 보이고 다시 시도 버튼을 둔다.

#### 4.3 규칙

이 기능이 지켜야 하는 업무 규칙을 하나씩 번호(BR-nn)를 붙여 적는다. 한 항목에 규칙 하나만. "적절히", "필요 시" 같은 말은 쓰지 않는다.

작성 예:

| 번호 | 규칙 |
|---|---|
| BR-01 | 결제 실패 목록에는 상태가 '결제 실패'인 주문만 나온다. 재시도 요청 뒤 '결제 대기'가 된 주문은 목록에서 빠진다 |
| BR-02 | 조회 역할은 재시도 요청 버튼을 볼 수 없다 |

#### 4.4 입력 검증

입력 필드마다 검증 규칙, 어디서 검증하는지(화면, 서버, 둘 다), 실패했을 때 보여 줄 문구 원문을 적는다.

작성 예:

| 필드 | 규칙 | 검증 위치 | 오류 문구 |
|---|---|---|---|
| 기간 | 시작일이 종료일보다 늦을 수 없다 | 화면, 서버 | "시작일은 종료일보다 앞이어야 합니다." |
| 기간 | 최대 90일 | 화면, 서버 | "조회 기간은 90일까지입니다." |

#### 4.5 처리

동작마다 실행 전에 갖춰져야 하는 것, 실행 뒤에 달라지는 것, 그 밖에 생기는 부수 효과(저장, 삭제, 외부 전송, 알림)를 적는다.

작성 예:

| 동작 | 전 조건 | 후 조건 | 부수 효과 |
|---|---|---|---|
| 목록 조회 | 로그인 상태 | 조건에 맞는 주문 목록 | 없음 |

#### 4.6 권한

동작과 역할을 표로 놓고 할 수 있는지 없는지 적는다. 할 수 없을 때 무엇이 보이는지도 적는다.

작성 예:

| 동작 | 관리자 | 담당자 | 조회 | 할 수 없을 때 |
|---|---|---|---|---|
| 목록 보기 | O | O | O | |
| 재시도 요청 | O | O | X | 버튼이 보이지 않는다 |

#### 4.7 메시지

확인 대화상자, 알림, 안내 문구를 원문 그대로 번호(MSG-nn)를 붙여 적는다. 언제 나오는지도 적는다.

작성 예:

| 번호 | 종류 | 문구 | 언제 |
|---|---|---|---|
| MSG-01 | 오류 | "목록을 불러오지 못했습니다. 잠시 후 다시 시도하세요." | 조회 실패 |
| MSG-02 | 확인 | "이 주문의 결제를 다시 시도합니다. 계속할까요?" | 재시도 버튼을 눌렀을 때 |

#### 4.8 데이터

읽고 쓰는 엔티티와 필드를 적는다. 데이터 모델 문서의 이름을 쓴다.

작성 예:

| 엔티티 | 필드 | 읽기/쓰기 |
|---|---|---|
| E-Order | id, orderer_name, amount, status, failed_at, failure_reason | 읽기 |

#### 4.9 연동

호출하는 API를 적는다. 계약 문서가 있으면 그 위치를, 없으면 필요한 것을 적는다.

작성 예:

| 호출 | 목적 | 계약 |
|---|---|---|
| GET /orders?status=payment_failed | 목록 조회 | docs/api/orders.md §3.1 |

#### 4.10 예외와 경계

동시에 수정할 때, 한도를 넘을 때, 시간이 초과될 때, 참조하던 것이 사라졌을 때 어떻게 하는지 적는다.

작성 예:

| 경우 | 동작 |
|---|---|
| 목록을 보는 사이 주문이 '결제 대기'로 바뀜 | 재시도 버튼을 누르면 "이미 처리 중인 주문입니다"(MSG-03)를 보이고 목록을 새로 고친다 |
| 조회가 10초를 넘음 | 중단하고 MSG-01 |

## 5. 추적

인수 조건마다 어느 기능의 어느 절이 받는지 적는다.

작성 예:

| 인수 조건 | 기능 | 절 |
|---|---|---|
| (1) 결제 실패 주문만 모아 볼 수 있다 | FN-01 | 4.1, 4.3 BR-01 |
| (2) 재시도 요청 시 상태 변경과 결과 갱신 | FN-02 | 4.2, 4.5 |

## 6. 미결과 가정

정하지 못한 것과 임시로 정한 것을 적는다. 되돌릴 수 있는 것은 `[가정]`, 되돌리기 어려운 것은 `[결정 필요]`로 표시하고 후자는 막힌 것으로 보고한다.

작성 예:

| 구분 | 내용 |
|---|---|
| [가정] | 페이지 크기 20건. 사용자 답 없음 |
| [결정 필요] | 재시도 횟수 제한. 결제 대행사 정책 확인 필요 |
