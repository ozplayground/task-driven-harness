# 코드 규칙

| 항목 | 내용 |
|---|---|
| 적용 범위 | 저장소 전체 |
| 참고 문서 | 이 문서가 근거로 삼은 문서. 링크로 적는다. `[요구사항 정의서](../prd/orders.md)` |

이 문서는 코드를 쓸 때 모두가 지키는 규칙을 정한다. 규칙마다 어떻게 검사하는지(도구, 명령, 테스트)를 적어서 사람이 기억에 의존하지 않게 한다. 자동으로 검사할 수 없는 규칙은 리뷰에서 무엇을 대조하는지 적는다. 취향은 적지 않는다. 구조가 강제하는 규칙만 적는다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 모듈 경계

어느 모듈이 어느 모듈을 import할 수 있는지, 공유는 어디를 통해서만 하는지 적는다.

작성 예:

| 규칙 | 검사 방법 |
|---|---|
| `orders.api`와 `orders.worker`는 서로 import하지 않는다. 공유는 `orders.core`만 | `tests/test_boundaries.py`가 import 그래프를 검사한다 |
| `web`은 DB에 직접 접근하지 않는다 | `web/`에 DB 드라이버 의존성이 없는지 `package.json` 확인 |

## 2. 이름 짓기

파일, 모듈, 테이블, 열, API 필드의 이름 규칙을 적는다.

작성 예:

| 대상 | 규칙 | 예 |
|---|---|---|
| Python 모듈·함수 | snake_case | `payment_retry.py`, `retry_payment()` |
| DB 테이블·열 | snake_case, 테이블은 복수형 | `orders`, `orderer_name` |
| API 필드 | camelCase | `ordererName` |
| 인덱스 | `ix_<테이블>_<열들>` | `ix_orders_status_failed_at` |

## 3. 에러와 로그

에러를 어떻게 만들고 돌려주는지, 로그에 무엇을 남기고 무엇을 남기면 안 되는지 적는다.

작성 예:

| 규칙 | 검사 방법 |
|---|---|
| API 에러는 `orders.core.errors`의 예외로만 낸다. 라우터에서 직접 응답을 만들지 않는다 | 리뷰에서 `HTTPException` 직접 사용 여부 대조 |
| 로그는 JSON 한 줄. 요청마다 `request_id` | `tests/test_logging.py` |
| 주문자 연락처는 로그에 남기지 않는다 (compliance C-04) | 테스트가 로그 출력에서 전화번호 형식을 검색해 0건인지 확인 |

## 4. 의존성

의존성을 어떻게 고정하고, 새로 추가할 때 무엇을 따르는지 적는다.

작성 예:

> 버전은 잠금 파일(`uv.lock`, `package-lock.json`)로 고정한다. 새 의존성은 최신 안정판을 쓰고, 다른 버전을 써야 하면 이유를 보고서에 적는다. 기본 스택(언어, 프레임워크, 저장소)의 버전은 아키텍처 문서가 정하고 여기서 바꾸지 않는다.

## 5. 포맷과 린트

도구와 명령을 적는다. CI나 리뷰 전에 무엇을 돌려야 하는지.

작성 예:

```sh
cd server && uv run ruff check . && uv run ruff format --check .
cd web && npm run lint
```

## 6. 테스트

테스트 파일 위치, 이름 규칙, 테스트 케이스 번호를 남기는 방법을 적는다.

작성 예:

> 테스트는 `server/tests/`에 모듈 구조를 따라 둔다. 테스트 케이스 문서의 번호를 함수 이름에 넣는다. 예: `test_tc09_payment_failed_list`. 외부 서비스는 실제로 부르지 않고 `tests/fakes/`의 가짜 서버를 쓴다.
