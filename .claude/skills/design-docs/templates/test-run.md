# 테스트 실행 보고 (날짜)

| 항목 | 내용 |
|---|---|
| 실행한 사람 | |
| 실행일 | |
| 대상 버전 | 커밋 해시 또는 태그 |
| 계획 문서 | [테스트 계획](test-plan.md) |

이 문서는 무엇을 돌렸고 결과가 무엇인지 기록한다. 계획에 있는 케이스는 빠짐없이 결과가 있어야 하고, 실패는 재현 방법과 함께, 돌리지 않은 것은 이유와 함께 적는다. 결과마다 확인할 수 있는 근거(명령, 출력 파일)를 남긴다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 요약

전체 케이스 수와 통과, 실패, 미실행 수를 쓴다. 통과 기준을 만족했는지 한 줄로 적는다.

작성 예:

> 케이스 45개 중 통과 43, 실패 1(TC-41), 미실행 1(TC-40, 이유는 5절). 통과 기준(실패 0) 미달. TC-41은 성능 기준 초과이며 원인은 4절.

## 2. 환경

실제로 돌린 환경의 구성 요소와 버전을 적는다. 계획의 환경과 다르면 무엇이 다른지 쓴다.

작성 예:

| 구성 | 버전 | 확인 방법 |
|---|---|---|
| Python | 3.13.2 | `python --version` |
| PostgreSQL | 18.1 | `SELECT version()` |
| OS | macOS 15, arm64 | 계획은 Linux였으나 로컬에서 실행 |

## 3. 케이스별 결과

케이스마다 결과와 근거를 적는다.

작성 예:

| 번호 | 결과 | 근거 |
|---|---|---|
| TC-09 | 통과 | `pytest tests/api/test_orders.py::test_tc09` 1 passed |
| TC-41 | 실패 | k6 결과 p95 1.4초. 출력 `reports/k6-2026-09-20.json` |
| TC-40 | 미실행 | 5절 |

## 4. 실패 상세

실패한 케이스마다 재현 절차, 실제로 관찰한 것, 기대했던 것을 적는다. 원인을 알면 적고 모르면 모른다고 쓴다.

작성 예:

| 번호 | 재현 절차 | 관찰 | 기대 | 원인 |
|---|---|---|---|---|
| TC-41 | 1만 건 시드 뒤 `k6 run tests/perf/list.js` | p95 1.4초 | 1초 이내 | ordererName 검색이 인덱스를 타지 않음. `EXPLAIN` 결과 seq scan |

## 5. 미실행과 이유

돌리지 않은 케이스와 이유, 언제 돌릴 수 있는지 적는다.

작성 예:

| 번호 | 이유 | 돌리려면 |
|---|---|---|
| TC-40 | k6 부하 생성기가 로컬 PC에서 초당 10건을 내지 못함 | 별도 부하 머신 |

## 6. 다시 돌리는 법

같은 결과를 재현하려면 어떤 명령을 어떤 순서로 돌리는지 적는다.

작성 예:

```sh
docker compose up -d --wait
cd server && uv run pytest -q
cd web && npx playwright test
```
