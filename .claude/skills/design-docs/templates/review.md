# task ID 리뷰 round 1

| 항목 | 내용 |
|---|---|
| 리뷰어 | reviewer |
| task | |
| 라운드 | 1 |
| 판정 | confirmed / needs-fix / inconclusive |

이 문서는 산출물이 완료 기준을 만족하는지 만든 쪽이 아닌 쪽이 판정한 기록이다. 보고서를 읽고 판정하지 않는다. 테스트는 직접 돌리고, 문서는 직접 열어 입력 문서와 대조한다. 내용이 타당한지(과잉 설계, 근거 부족 등)는 여기서 보지 않는다. 그건 critic의 비평이다. 지적마다 번호를 붙이고 재현 방법을 적어 만든 쪽이 그대로 따라 할 수 있게 한다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 검사 계획

판정을 시작하기 전에 완료 기준마다 무엇을 실행하고 무엇을 대조할지 적는다. 실행할 수 없는 기준은 여기서 표시해 둔다.

작성 예:

| 기준 | 실행할 것 / 대조할 것 | 상태 |
|---|---|---|
| 엔드포인트 2개, TC-09~15 | `pytest tests/api -q` 직접 실행. curl로 재현 | 끝 |
| 조회 역할 403 | 조회 역할 토큰으로 curl | 끝 |
| 코드 규칙 | ruff 두 명령 실행. 에러 형식은 코드 규칙 §3과 대조 | 끝 |
| 화면 흐름 | 실행할 수 없음 (화면은 I3) → inconclusive 후보 | — |

## 2. 완료 기준 확인

기준마다 결과와 확인 방법을 적는다. 확인 방법은 직접 실행한 명령과 출력, 또는 대조한 문서의 위치다. 보고서 문장을 옮겨 적는 것은 확인이 아니다. 문서 산출물이면 템플릿의 절이 다 있는지, 입력 문서의 항목이 빠짐없이 반영됐는지를 대조한다.

작성 예:

| 기준 | 결과 | 확인 방법 |
|---|---|---|
| 엔드포인트 2개, TC-09~15 | 충족 | `pytest tests/api -q` 7 passed. curl로 202와 409 직접 확인 |
| 조회 역할 403 | 충족 | 조회 토큰으로 POST → 403 |
| 코드 규칙 | 불충족 | 409 응답이 `{"detail": ...}` 형식. 코드 규칙 §3 공통 에러 형식 위반 |

## 3. 범위

소유 경로 밖을 바꿨는지, 요청에 없는 것을 바꿨는지 적는다. "같이 고친 버그"에 적힌 것은 관련성이 타당한지만 본다. 실행자 보고의 "명세에 없어 내가 정한 것"에 아키텍처 문서가 정했어야 하는 것(언어, 런타임, 프레임워크, 저장소, 인프라와 그 버전, 공통 규약)이 들어 있으면 범위 이탈로 적는다.

작성 예:

> 소유 경로 밖 변경: 없음. `git diff --name-only feature/order-service...feature/order-service/i1` 3개 파일 모두 `server/orders/api/**`, `server/tests/api/**` 안.
> 요청 밖 변경: 없음. 같이 고친 버그 1건은 소유 파일 안이고 재현 테스트가 있다.
> 내가 정한 것: 재시도 한도 기준 시각 UTC — 공통 규약 범위 안, 문제 없음.

## 4. 지적 사항

지적마다 번호(task-Fn), 심각도, 위치, 무엇이 기준과 어긋나는지, 재현 방법. 심각도는 blocker(완료 기준을 못 채웠거나 소유 경로 밖을 바꿈), major(기준은 채웠지만 특정 입력에서 깨지거나 요청 밖 변경), minor(기록만, 재작업 안 함).

작성 예:

| 번호 | 심각도 | 위치 | 내용 | 재현 |
|---|---|---|---|---|
| I1-F1 | blocker | `api/routers/orders.py:131` | 409 응답이 공통 에러 형식이 아니다 | 같은 주문에 재시도 두 번 → 응답 본문 확인 |
| I1-F2 | major | `api/routers/orders.py:88` | 기간 91일을 주면 422 대신 200 | curl로 from/to 91일 |

## 5. 이전 라운드 지적 (round 2부터)

이전 라운드 지적마다 해소됐는지 직접 확인해 적는다. round 2부터는 새 지적을 회귀(고치다 깨진 것)와 blocker만 올린다.

작성 예:

| 번호 | 상태 | 확인 |
|---|---|---|
| I1-F1 | resolved | 409 응답 `{"error": {...}}` 확인, curl 출력 |
| I1-F2 | open | 여전히 200 |

## 6. 판정

세 가지 중 하나를 쓰고 이유를 한 줄로 적는다. confirmed는 모든 기준 충족에 blocker·major 없음. needs-fix는 blocker나 major가 있음. inconclusive는 판정할 수 없는 기준이 있음(무엇이 있어야 판정되는지 적는다).

작성 예:

> needs-fix. I1-F1(blocker), I1-F2(major). 재작업 대상: I1-F1, I1-F2.
