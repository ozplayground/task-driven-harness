# 주문 조회 설계

| 항목 | 내용 |
|---|---|
| 참고 문서 | [기능 명세서 REQ-01 주문 조회](../../fsd/orders/REQ-01-order-search.md), [아키텍처](../architecture.md) |

이 문서는 기능 명세서 하나(요구사항 하나)를 받아 그 기능을 시스템 안에서 어떻게 만들지 정한다. 기능 명세서는 무엇이 되어야 하는지를 말하고, 이 문서는 어느 구성 요소가 어떤 순서로 어떤 데이터를 다뤄 그것을 만드는지를 말한다. API 명세와 데이터 모델은 이 문서들에서 도출된다. 구현자는 이 문서대로 만들고 구조를 정하지 않는다.

제목은 "<요구사항 주제> 설계"다. 파일은 기능 명세서와 같은 요구사항 번호를 쓴다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 개요

이 기능이 무엇을 하고 어떤 구성 요소를 거치는지 다섯 줄 안에 쓴다. 이 절만 읽어도 어디에 무엇이 생기는지 보여야 한다.

작성 예:

> 담당자가 백오피스에서 조건을 넣어 주문 목록을 보고 주문 하나를 열어 본다. 화면(web)이 API(api)의 주문 조회 엔드포인트를 부르고, api는 주문 저장소를 읽어 목록과 상세를 돌려준다. 새 구성 요소는 없고 api에 주문 조회 모듈이 하나 생긴다.

## 2. 관여하는 구성 요소

아키텍처 문서의 실행 단위와 모듈 가운데 이 기능이 거치는 것을 적고, 이 기능에서 각각이 맡는 책임을 쓴다. 새로 생기는 모듈이 있으면 어느 실행 단위 안에 생기는지, 왜 기존 모듈로 안 되는지 쓴다.

작성 예:

| 구성 요소 | 이 기능에서의 책임 | 신규 |
|---|---|---|
| web 주문 목록 화면 | 검색 조건 입력, 목록·상세 표시 | 아니오 |
| api `orders.search` 모듈 | 조건 검증, 저장소 조회, 응답 조립 | 예 — 기존 주문 모듈은 생성·상태 변경만 다룬다 |
| 주문 저장소 | 주문·주문 항목 읽기 | 아니오 |

## 3. 처리 흐름

기능 명세서의 기능(FN)마다 요청이 들어와서 응답이 나갈 때까지 구성 요소가 어떤 순서로 무엇을 하는지 쓴다. 정상 흐름 다음에 실패 흐름을 쓴다. 문장 순서로 충분하면 문장으로, 분기가 많으면 표나 순서도로.

작성 예:

**주문 목록 조회.** web이 검색 조건(기간, 상태, 주문자)을 담아 api를 부른다. api는 조건을 검증하고, 기간이 없으면 최근 30일로 채운다. 저장소에서 조건에 맞는 주문을 주문일 내림차순으로 20건씩 읽어 총 건수와 함께 돌려준다. 조건이 틀리면 어느 조건이 왜 틀렸는지 담아 400을 돌려주고 web은 그 조건 입력란에 표시한다.

**주문 상세 조회.** web이 주문 번호로 api를 부른다. api는 주문과 주문 항목, 결제 시도 기록을 읽어 하나로 돌려준다. 없는 번호면 404.

## 4. 데이터

이 기능이 읽고 만들고 바꾸는 데이터를 적는다. 어떤 엔티티의 어떤 필드를 쓰는지, 새로 필요한 필드나 인덱스가 있는지, 상태를 바꾸면 어떤 전이인지. 데이터 모델은 이 절들을 모아 만든다.

작성 예:

| 데이터 | 읽기/쓰기 | 필드 | 새로 필요한 것 |
|---|---|---|---|
| 주문 | 읽기 | 번호, 주문일, 상태, 주문자 이름, 금액 | (주문일, 상태) 인덱스 |
| 주문 항목 | 읽기 | 상품, 수량, 단가 | 없음 |
| 결제 시도 | 읽기 | 시각, 결과, 실패 이유 | 없음 |

## 5. 인터페이스

구성 요소 사이, 화면과 서버 사이에 주고받아야 하는 것을 적는다. 요청에 무엇이 들어가고 응답에 무엇이 나오는지, 실패는 어떻게 알리는지. 정확한 필드 이름·타입·상태 코드는 API 명세에서 정하므로 여기서는 무엇이 필요한지까지만 쓴다.

작성 예:

| 인터페이스 | 요청 | 응답 | 실패 |
|---|---|---|---|
| 주문 목록 조회 | 기간, 상태, 주문자, 페이지 | 주문 요약 목록, 총 건수 | 조건 오류(어느 조건인지) |
| 주문 상세 조회 | 주문 번호 | 주문, 항목, 결제 시도 | 없는 번호 |

## 6. 규칙의 위치

기능 명세서의 검증 규칙, 권한, 문구, 예외가 어느 구성 요소에서 처리되는지 적는다. 한 규칙이 두 곳에서 처리되면 어느 쪽이 기준인지 쓴다.

작성 예:

| 규칙 | 처리 위치 | 비고 |
|---|---|---|
| 기간은 최대 1년 | api (검증), web (입력 제한) | api가 기준 |
| 조회 권한: 담당자 이상 | api | web은 메뉴 표시만 |
| 연락처 마스킹 | api 응답 조립 | 원문은 응답에 넣지 않는다 |

## 7. 비기능 처리

성능, 동시성, 트랜잭션 경계, 재시도, 외부 연동 실패 가운데 이 기능에 해당하는 것을 적는다. 해당 없으면 없다고 쓴다.

작성 예:

> 목록 조회는 읽기만 하므로 트랜잭션 없이 읽는다. 총 건수는 같은 조건으로 한 번 더 세지 않고 페이지 조회와 같은 쿼리에서 얻는다. 응답 시간 목표는 1초 안(NFR-03)이고 (주문일, 상태) 인덱스로 맞춘다.

## 8. 결정과 근거

이 기능을 이렇게 만드는 이유 가운데 다른 방법도 있었던 것을 적는다. 고려한 방법, 고른 이유, 아직 정하지 않은 것과 언제 정할지. 되돌리기 어려운 것은 결정 기록으로 올리고 여기서는 번호만 가리킨다.

작성 예:

| 결정 | 다른 방법 | 고른 이유 |
|---|---|---|
| 총 건수를 페이지 쿼리에서 함께 얻는다 | 별도 count 쿼리 | 쿼리 한 번으로 응답 시간 목표를 맞춘다 |
| 상세에 결제 시도를 포함한다 | 별도 엔드포인트 | 화면이 항상 함께 보여 준다 (SCR-03) |
