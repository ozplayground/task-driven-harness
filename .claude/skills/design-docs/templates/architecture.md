# 아키텍처 문서

| 항목 | 내용 |
|---|---|
| 참고 문서 | 이 문서가 근거로 삼은 문서. 링크로 적는다. `[요구사항 정의서](../prd/orders.md)` |

이 문서는 시스템의 구조, 기술 스택, 모든 모듈이 함께 지키는 규약을 정한다. 뒤에 오는 설계 문서, 계약, 구현은 모두 이 문서를 전제로 만들어진다. 그래서 이 문서에서 정하지 않은 것은 뒤에서 누군가 임의로 정하게 된다. 정할 수 있는 것은 여기서 정하고, 정하지 못한 것은 정하지 못했다고 쓴다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 개요

이 시스템이 무엇이고 어떻게 구성되는지 열 줄 안에 쓴다. 구조 스타일(모놀리스인지, 서비스가 나뉘는지), 실행 단위가 몇 개인지, 저장소는 무엇인지, 실행 단위끼리 어떻게 통신하는지, 어디에 배포되는지가 들어가면 된다. 이 절만 읽어도 시스템의 모양이 그려져야 한다.

작성 예:

> 주문 관리 서비스는 백오피스 웹, API 서버, 결제 결과를 처리하는 작업자 세 실행 단위로 나뉜다. 저장소는 PostgreSQL 하나이고, 결제 결과 처리처럼 오래 걸리는 일은 PostgreSQL 위에서 도는 작업 큐로 넘긴다. 웹과 API는 HTTP로, API와 작업자는 큐로만 통신한다. 로컬 개발은 Docker Compose로 DB만 띄우고 나머지는 호스트에서 실행한다.

## 2. 요구와 제약

구조를 결정하는 데 영향을 준 요구와 제약을 적는다. 수치로 적을 수 있는 것은 수치로 적고, 어디서 온 요구인지 출처를 단다. 사용자에게 물었지만 답을 받지 못해 가정한 값은 `[가정]`이라고 표시한다.

다음은 반드시 다룬다. 사용자 규모, 데이터 양, 처리량, 응답 시간, 가용성, 팀 규모와 역량, 예산, 연동해야 하는 기존 시스템, 규제 대상 데이터.

작성 예:

| 항목 | 값 | 출처 |
|---|---|---|
| 사용자 규모 | 백오피스 사용자 30명 이하 | PRD NFR-01 |
| 처리량 | 주문 생성 초당 10건 | PRD NFR-03 |
| 가용성 | 업무 시간 중 99% | [가정] 사용자 답 없음 |
| 팀 | 개발자 2명, Python과 TypeScript | 사용자 답 (notes 2026-09-18) |

## 3. 시스템 구성

실행 단위(프로세스, 서비스)를 하나씩 적는다. 각 실행 단위가 무엇을 책임지는지, 무엇을 하지 않는지, 누구와 어떤 방식으로 통신하는지를 쓴다. "무엇을 하지 않는지"가 중요하다. 경계가 흐리면 구현할 때 두 모듈이 같은 일을 하거나 아무도 안 하게 된다.

그 다음 주요 데이터 흐름을 서술한다. 사용자의 요청 하나가 어떤 실행 단위를 거쳐 어디에 저장되고 어떻게 응답되는지를 순서대로 쓴다.

작성 예:

| 실행 단위 | 책임 | 하지 않는 것 | 통신 |
|---|---|---|---|
| web | 백오피스 화면. 세션 쿠키를 토큰으로 바꿔 API를 부른다 | DB에 직접 접근하지 않는다 | api와 HTTP |
| api | 인증, 주문 CRUD, 결제 요청 접수 | 결제 결과를 직접 기다리지 않는다 | web과 HTTP, worker와 큐 |
| worker | 결제 결과 조회, 주문 상태 갱신 | 사용자 요청을 받지 않는다 | 결제 대행사와 HTTP |

> 결제 흐름: 사용자가 결제를 요청하면 api가 주문 상태를 '결제 대기'로 바꾸고 작업을 큐에 넣는다. worker가 결제 대행사에서 결과를 받아 주문 상태를 '결제 완료' 또는 '결제 실패'로 바꾼다.

## 4. 기술 스택

계층마다 무엇을 쓰는지, 어떤 버전을 쓰는지, 왜 그것을 골랐는지를 쓴다. 이름만 적고 버전을 비우면 구현하는 쪽이 아무 버전이나 쓰게 되므로 버전까지 적는다. 고른 이유는 "익숙해서" 같은 한 마디가 아니라, 어떤 요구나 제약 때문에 다른 후보 대신 이것을 골랐는지를 쓴다. 자세한 비교는 결정 기록(ADR)에 있고 여기서는 그 번호를 가리킨다.

다음 계층은 빠뜨리지 않는다. 언어와 런타임(실행 단위마다), 프레임워크(실행 단위마다), 데이터 저장소, 큐나 메시지 전달, 인프라와 컨테이너 이미지, 의존하는 핵심 SDK. 해당 계층이 없으면 없다고 쓴다.

작성 예:

| 계층 | 선택 | 버전 | 고른 이유 | 결정 기록 |
|---|---|---|---|---|
| 언어·런타임 (api, worker) | Python | 3.13 | 팀이 다루는 언어. 선택 당시 최신 안정판 | ADR-006 |
| 프레임워크 (api) | FastAPI | 0.118 | 비동기 지원과 OpenAPI 자동 생성이 필요했다. 최신 안정판 | ADR-006 |
| 데이터 저장소 | PostgreSQL | 18 | 관계형 데이터이고 큐를 같은 DB에 둘 수 있다. 최신 메이저 | ADR-003 |
| 큐 | procrastinate | 3.9 | 추가 인프라 없이 PostgreSQL 위에서 동작한다 | ADR-002 |
| 컨테이너 이미지 | postgres | 18-alpine | 저장소 버전과 맞췄다 | ADR-007 |
| 핵심 SDK | 없음 | | | |

## 5. 공통 규약

모든 모듈이 같은 방식으로 처리해야 하는 것을 정한다. 인증과 권한, 에러 응답 형식, 설정과 시크릿을 어디에 두는지, 로그 형식과 요청 추적, 시간대와 단위. 여기서 정하지 않으면 모듈마다 다르게 만들어진다.

작성 예:

| 항목 | 규약 | 결정 기록 |
|---|---|---|
| 인증·권한 | 자체 발급 JWT. 역할은 관리자, 담당자, 조회 셋 | ADR-004 |
| 에러 응답 | `{"error": {"code", "message", "details"}}` 형식으로 통일 | ADR-005 |
| 시크릿 | 값은 환경변수에 두지 않고 권한 0600 파일의 경로만 넘긴다 | ADR-004 |
| 시간·단위 | 저장은 UTC, 화면은 Asia/Seoul. 금액은 원 단위 정수 | ADR-005 |

## 6. 데이터 소유권

데이터 종류마다 어느 모듈이 쓰고(생성·수정) 어느 모듈이 읽기만 하는지 적는다. 한 데이터를 두 모듈이 쓰면 충돌하므로 쓰는 쪽은 하나여야 한다.

작성 예:

| 데이터 | 쓰는 모듈 | 읽는 모듈 |
|---|---|---|
| 주문 | api (worker는 상태만 바꾼다) | api |
| 결제 시도 기록 | worker | api |

## 7. 저장소 구조

코드 저장소의 최상위 구조와 각 디렉터리가 3절의 어느 실행 단위에 대응하는지 적는다.

작성 예:

| 경로 | 무엇 | 대응 |
|---|---|---|
| `server/orders/api` | API 서버 | api |
| `server/orders/core` | 도메인 모델과 DB 접근 | api와 worker가 함께 쓴다 |
| `web/` | 백오피스 | web |

## 8. 배포

어떤 환경에 어떤 형태로 배포하는지 적는다. 환경(로컬, 스테이징, 운영)마다 실행 단위를 어디서 어떻게 띄우는지, 인프라 정의 파일이 어디 있는지. 이번 범위에서 정하지 않는 환경은 정하지 않는다고 쓰고 언제 정할지 적는다.

작성 예:

| 환경 | 실행 방식 | 인프라 정의 |
|---|---|---|
| 로컬 | DB는 Docker Compose, 나머지는 호스트에서 실행 | `compose.yaml` |
| 운영 | 이번 범위에서 정하지 않는다. 운영 배포 요구가 생기면 정한다 | |

## 10. 이 문서가 요구하는 후속 설계

이 구조 때문에 구현 전에 반드시 있어야 하는 문서를 적는다. 예를 들어 웹과 API를 따로 개발한다면 API 계약이 먼저 있어야 하고, 큐를 쓴다면 작업 형식이 정해져야 한다. 문서마다 무엇을 입력으로 삼는지, 어느 문서가 먼저 있어야 하는지 적는다.

작성 예:

| 문서 | 필요한 이유 | 입력 | 선행 |
|---|---|---|---|
| UX 설계 | 백오피스 화면이 있다 | PRD | 없음 |
| 디자인 시스템 | 프론트엔드 task가 공통 컴포넌트를 써야 한다 | UX 설계 | UX 설계, FSD |
| 데이터 모델 | 주문과 결제 시도 테이블, 상태 전이를 정해야 한다 | PRD, FSD REQ-03 | 없음 |
| API 계약 (orders) | web과 api를 따로 개발한다 | FSD, 데이터 모델 | 데이터 모델 |
