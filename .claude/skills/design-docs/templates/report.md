# task ID 제목

| 항목 | 내용 |
|---|---|
| 작성자 | task를 맡은 에이전트 |
| task | |
| 라운드 | 1 (재작업이면 2, 3) |
| 상태 | 계획 / 진행 중 / 완료 |
| 참고 문서 | 이 문서가 근거로 삼은 문서. 링크로 적는다. `[요구사항 정의서](../prd/orders.md)` |

이 보고서는 task 하나를 맡은 쪽이 쓴다. 시작할 때 계획을 먼저 쓰고, 진행하면서 진행 상태를 고쳐 쓰고, 끝나면 완료 보고로 마무리한다. 리더는 이 파일을 읽고 리뷰어를 부른다. "완료했다"는 말 대신 무엇을 어떻게 확인했는지를 쓴다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 계획

브리프를 읽고 아무것도 만들기 전에 쓴다. 할 일을 산출물 단위로 나누고, 각각이 어느 완료 기준을 채우는지, 어떻게 확인할지 적는다. 모르는 것과 막힐 수 있는 것을 표 아래에 적는다. 입력 문서에 없어서 만들 수 없는 완료 기준이 보이면 여기서 멈추고 "막힌 것"에 적는다.

작성 예:

| 번호 | 할 일 | 채우는 완료 기준 | 확인 방법 | 상태 |
|---|---|---|---|---|
| 1 | 입력 문서 읽기 (FSD REQ-02, 계약 §3, 데이터 모델) | — | — | 끝 |
| 2 | GET /orders 결제 실패 필터 | 기준 1 | TC-09 통과 | 진행 |
| 3 | POST /orders/{id}/payment-retry | 기준 1, 2 | TC-10, 14, 15 통과 | 남음 |
| 4 | 전체 테스트와 린트 | 기준 3 | 실행 결과 | 남음 |

> 모르는 것: 재시도 하루 한도의 기준 시각(UTC인지 KST인지) — FSD에 없음. UTC로 가정, 되돌릴 수 있음.
> 막힐 수 있는 것: 계약 §3.2의 202 응답에 `retryCount` 필드가 있는데 데이터 모델에 없다. 확인 필요.

## 2. 진행 상태

중간에 끊겨도 다음 사람이 이어 갈 수 있게 쓴다. 끝난 것, 하고 있는 것, 남은 것, 다음 사람이 어디서부터 하면 되는지. 완료 보고를 쓸 때 이 절은 지운다.

작성 예:

> 끝: 2번 (TC-09 통과).
> 지금: 3번, 재시도 등록까지 됐고 하루 한도 검사 작성 중 (`api/routers/orders.py` 120행 부근).
> 남음: 3번 나머지, 4번.
> 다음 사람: 한도 검사부터. 한도 상수는 `core/limits.py`에 두기로 했다.

## 3. 완료 기준

브리프의 완료 기준을 하나씩 적고, 각각을 어떤 수준으로 확인했는지와 그 증거를 적는다. 수준은 넷 중 하나다. 실행 검증(이번 작업 중 직접 실행해 출력이 있다), 산출물 대조(문서나 코드를 열어 항목을 맞춰 봤다), 미검증(확인하지 못했다, 이유를 쓴다), 해당 없음.

작성 예:

| 기준 | 확인 수준 | 증거 |
|---|---|---|
| 계약 §3의 엔드포인트 2개 구현, TC-09~15 통과 | 실행 검증 | `uv run pytest tests/api/test_orders.py -q` → 7 passed |
| 조회 역할은 재시도 403 | 실행 검증 | TC-13 통과, curl로 403 확인 |
| 코드 규칙 준수 | 실행 검증 | `ruff check .`, `ruff format --check .` 통과 |
| 화면에서 재시도 흐름 | 미검증 | 화면은 I3 몫. API만 확인 |

## 4. 변경한 파일

실제로 만들거나 고친 파일을 모두 적고 커밋 해시를 적는다. 커밋에 든 파일과 같아야 한다. 여기 없는데 바뀐 파일이 있으면 범위 이탈로 잡힌다.

작성 예:

커밋: `a1b2c3d` (feat: 결제 실패 목록·재시도 API)

- `server/orders/api/routers/orders.py` (수정)
- `server/orders/core/limits.py` (신규)
- `server/tests/api/test_orders.py` (수정)

## 5. 같이 고친 버그

요청받지 않았지만 이 task와 관련이 있어서 함께 고친 버그를 적는다. 관련이 있다는 근거, 원인, 고친 방법, 고쳐졌다는 증명. 요청 밖 발견과 섞지 않는다.

작성 예:

| 증상 | 관련성 | 원인 | 수정 | 증명 |
|---|---|---|---|---|
| 상태 필터에 없는 값을 주면 500 | 내 소유 파일(`orders.py`) | 값 검증 없음 | 허용 값 검사 추가 | 재현 테스트 `test_invalid_status` 통과 |

## 6. 명세에 없어 내가 정한 것

입력 문서에 없어서 스스로 정한 것을 적는다. 무엇을 정했는지, 왜 그렇게 정했는지(비교한 후보), 되돌릴 수 있는지. 언어·런타임·프레임워크·저장소·인프라와 그 버전, 통신 방식, 에러 형식처럼 아키텍처 문서가 정할 것은 여기 적지 않고 "막힌 것"에 적는다.

작성 예:

| 정한 것 | 이유 | 되돌릴 수 있나 |
|---|---|---|
| 재시도 한도 기준 시각을 UTC로 | 저장이 UTC(공통 규약)라 맞췄다. KST 자정 기준도 가능했으나 규약과 다르다 | 예, 상수 하나 |

## 7. 요청 밖 발견

손대지 않은 문제를 적는다. 위치, 증상, 재현되는지.

작성 예:

> `web/lib/date.ts` 12행 — 시간대 변환이 서머타임을 고려하지 않는 것으로 보임. 재현은 안 해 봤다.

## 8. 막힌 것

입력 문서가 없거나 서로 달라서 하지 못한 것, 소유 경로 밖을 바꿔야 해서 멈춘 것을 적는다. 없으면 "없음".

작성 예:

> 계약 §3.2의 `retryCount`가 데이터 모델에 없다. 데이터 모델에 열이 추가돼야 응답을 만들 수 있다. 임시로 필드를 빼지 않고 여기서 멈췄다.

## 9. 다음에 필요한 것

이 산출물을 쓰려면 있어야 하는 것, 이 task 때문에 새로 필요해진 것을 적는다. 리더가 이 절을 보고 다음 task를 정한다. 없으면 "없음".

작성 예:

> - 데이터 모델에 `retry_count` 열 추가 (8절).
> - I3(화면)는 재시도 요청 응답이 202이고 상태가 `payment_pending`으로 오는 것을 전제로 하면 된다.

## 10. 자기 검증

보고 전에 세 가지를 대조하고 결과를 적는다. 계획대로 다 했는지, 완료 기준을 각각 어떤 수준으로 확인했는지, 바뀐 파일이 전부 소유 경로 안인지. 마지막으로 브리프를 준 사람 입장에서 다시 읽고 고친 것을 적는다.

작성 예:

| 대조 | 결과 |
|---|---|
| 계획 대비 | 4행 전부 끝. 3번은 한도 검사를 따로 뺐다 |
| 완료 기준 대비 | 기준 1~3 실행 검증, 기준 4 미검증 (화면 없음) |
| 범위 대비 | 바뀐 파일 3개 모두 소유 경로 안 |
| 다시 읽고 고친 것 | 409 응답이 공통 에러 형식과 달랐다 → 고침 |
