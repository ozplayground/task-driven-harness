# 조사 주제

| 항목 | 내용 |
|---|---|
| 조사 종류 | 질문 하나에 답하는 조사 / 여러 대상을 같은 축으로 비교하는 벤치마크 |
| 이 조사를 요청한 문서 | |
| 참고 문서 | 이 문서가 근거로 삼은 문서. 링크로 적는다. `[요구사항 정의서](../prd/orders.md)` |

이 문서는 질문 하나에 근거 있는 답을 낸다. 답보다 근거가 중요하다. 근거가 없는 답은 추정으로 따로 적는다. 벤치마크라면 비교 축이 요구에서 나와야 하고, 축마다 대상별 값을 근거와 함께 적는다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 질문

답해야 할 질문을 닫힌 형태로 쓴다. "큐를 뭘로 할까"가 아니라 "초당 10건, 추가 인프라 없이, 주문 저장과 원자적으로 작업을 등록할 수 있는 큐는 무엇인가"처럼 조건이 드러나게 쓴다. 하위 질문이 있으면 나눈다.

작성 예:

> 주문 서비스의 결제 결과 처리에 쓸 작업 큐로 무엇이 적합한가?
> - 추가 인프라 없이 PostgreSQL만으로 동작하는 선택지가 있는가?
> - 주문 저장과 작업 등록을 한 트랜잭션에 넣을 수 있는가?
> - 초당 10건, 하루 5천 건을 감당하는가?

## 2. 답

결론을 열 줄 안에 쓴다. 벤치마크라면 "이 기준이면 A, 저 기준이면 B"처럼 기준에 따라 답이 갈리는 것을 그대로 쓴다.

작성 예:

> 추가 인프라를 두지 않는 것이 기준이면 procrastinate가 맞다. PostgreSQL 위에서 동작하고 주문 INSERT와 작업 등록을 한 트랜잭션에 넣을 수 있다(근거 3). 처리량은 문서상 초당 수백 건이라 요구를 넉넉히 넘는다(근거 4). Redis 운영이 이미 있다면 RQ가 처리량에서 유리하지만, 지금은 Redis가 없다.

## 3. 근거

답을 이루는 주장을 하나씩 적고, 주장마다 출처, 출처의 등급, 다른 사람이 확인하는 방법을 적는다. 등급은 공식 문서·실측(1차), 다른 사람의 정리(2차), 의견으로 나눈다. 1차 근거가 없는 주장은 "미확인"이라고 쓴다.

작성 예:

| 번호 | 주장 | 출처 | 등급 | 확인 방법 |
|---|---|---|---|---|
| 1 | procrastinate는 PostgreSQL만 있으면 동작한다 | procrastinate 공식 문서 "Requirements" | 1차 | 문서 해당 절 |
| 3 | 작업 등록을 기존 트랜잭션 안에서 할 수 있다 | 공식 문서 "Deferring jobs in a transaction" | 1차 | 로컬에서 `configure(connection=...)`로 실측 |
| 4 | 처리량 초당 수백 건 | 유지보수자 블로그 | 2차 | 부하 테스트로 확인 필요 |

## 4. 비교 (벤치마크일 때)

비교 축을 먼저 적고, 각 축이 어느 요구에서 왔는지 쓴다. 대상마다 축별 값을 적되 근거가 있는 값만 적고 없으면 "미확인"이라고 쓴다. 벤치마크가 아니면 이 절은 "해당 없음"으로 둔다.

작성 예:

선정 기준: 요구(NFR-03 처리량, 운영 부담 최소)에서 나온 축 네 개.

| 축 (출처) | procrastinate | RQ | 결제사 웹훅만 |
|---|---|---|---|
| 추가 인프라 (사용자 답) | 없음 (근거 1) | Redis 필요 | 없음 |
| 원자적 등록 (ADR-001) | 가능 (근거 3) | 불가 | 해당 없음 |
| 처리량 (NFR-03) | 초당 수백 건 (근거 4, 2차) | 초당 수천 건 (공식 문서) | 미확인 |
| 유실 복구 | 재시도 내장 | 재시도 내장 | 없음 |

## 5. 가져올 것과 버릴 것 (벤치마크일 때)

비교 대상에서 우리가 가져올 것과 가져오지 않을 것을 이유와 함께 적는다.

작성 예:

| 대상의 무엇 | 가져옴 / 버림 | 이유 |
|---|---|---|
| procrastinate의 주기 작업 기능 | 버림 | 이번 범위에 주기 작업이 없다 |
| RQ의 작업 결과 보관 방식 | 가져옴 | 결제 시도 이력 저장에 같은 방식을 쓴다 |

## 6. 반대 근거

답과 반대되는 근거를 찾아본 결과를 적는다. 찾았으면 무엇이고 답에 어떤 영향을 주는지, 찾지 못했으면 어디를 찾아봤는지 쓴다.

작성 예:

> procrastinate가 대량 작업에서 테이블 잠금 경합이 생긴다는 이슈(GitHub #xxx)가 있다. 하루 5천 건 규모에서는 해당하지 않지만 초당 100건을 넘으면 다시 봐야 한다.

## 7. 확인하지 못한 것

찾아봤지만 답을 얻지 못한 것과, 어디까지 찾아봤는지 적는다.

작성 예:

> procrastinate의 실제 처리량은 공식 문서에 수치가 없다. 유지보수자 블로그 값만 있어 2차 근거로 남겼다.

## 8. 추정

근거가 약하지만 판단에 참고할 만한 것을 적는다. 답과 섞지 않는다.

## 9. 이 답으로 할 수 있는 것

이 조사 결과로 바로 결정할 수 있는 것과, 더 조사해야 결정되는 것을 적는다.

작성 예:

> 바로 결정할 수 있는 것: 큐 선택(ADR-002).
> 더 조사해야 하는 것: 처리량 실측. 부하 테스트 환경이 있어야 한다.
