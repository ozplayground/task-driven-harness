# 제품 이름 요구사항 정의서 (PRD)

| 항목 | 내용 |
|---|---|
| 참고 문서 | 이 문서가 근거로 삼은 문서. 링크로 적는다. `[요구사항 정의서](../prd/orders.md)` |

이 문서는 무엇을 왜 만드는지를 정한다. 요구사항 하나하나에 번호(REQ-nn)를 붙이고, 각 요구사항이 어느 기능 명세서(FSD)에서 상세화되는지까지 연결한다. 어떻게 만드는지(구조, 스택, 화면 상세)는 이 문서의 범위가 아니다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 배경과 문제

누가 지금 무엇 때문에 불편한지, 이 제품이 없으면 어떤 일이 생기는지 쓴다. 해결책을 쓰지 않고 문제만 쓴다.

작성 예:

> 운영팀은 주문 상태를 결제 대행사 관리 화면과 스프레드시트를 오가며 확인한다. 하루 5천 건 중 결제 실패 건을 놓쳐 배송이 늦어지는 일이 주 2~3회 생긴다.

## 2. 목표와 측정

이 제품으로 이루려는 것을 측정할 수 있는 형태로 쓴다. 목표마다 무엇을 어떻게 재고, 얼마가 되면 달성인지 적는다.

작성 예:

| 목표 | 측정 방법 | 목표값 |
|---|---|---|
| G1 결제 실패 건을 놓치지 않는다 | 결제 실패 후 담당자 확인까지 걸린 시간 | 1시간 이내 100% |
| G2 주문 확인에 드는 시간을 줄인다 | 담당자 1인당 하루 주문 확인 소요 시간 | 2시간 → 30분 |

## 3. 사용자와 역할

이 제품을 쓰는 사람을 역할별로 적는다. 역할마다 누구인지, 무엇을 하려고 쓰는지 적는다. 권한 차이가 있으면 여기서 드러나야 한다.

작성 예:

| 역할 | 누구 | 하는 일 |
|---|---|---|
| 관리자 | 운영팀장 | 사용자 등록, 권한 부여, 전체 주문 조회 |
| 담당자 | 운영팀원 | 주문 조회, 결제 실패 건 처리 |
| 조회 | CS팀 | 주문 조회만 |

## 4. 범위

이번에 만드는 것과 만들지 않는 것을 적는다. 만들지 않는 것이 더 중요하다. 여기 적히지 않은 기능은 나중에 누군가 추가하게 된다. 만들지 않기로 한 이유가 있으면 짧게 적는다.

작성 예:

> 포함: 주문 조회, 결제 상태 확인, 결제 실패 건 재시도 요청, 사용자와 권한 관리
> 제외: 배송 추적(배송사 API 연동은 다음 단계), 환불 처리(결제 대행사 화면에서 계속 처리), 모바일 화면

## 5. 요구사항

요구사항을 하나씩 적는다. 요구사항 하나는 사용자가 하나의 목적으로 쓰는 기능 단위다. 각 요구사항에는 번호, 이름, 정의(누가 무엇을 어디까지 할 수 있는지), 우선순위, 인수 조건, 상세화하는 FSD 파일 경로를 적는다. 인수 조건은 "됐다/안 됐다"를 판정할 수 있는 문장으로 쓴다.

작성 예:

### REQ-01 주문 조회

- 정의: 담당자와 조회 역할이 주문을 기간, 상태, 주문자 이름으로 찾아 목록과 상세를 본다.
- 우선순위: 필수
- 인수 조건:
  1. 최근 90일 주문을 기간·상태·주문자 이름으로 걸러서 볼 수 있다.
  2. 목록에서 주문을 고르면 상세(주문 항목, 결제 상태, 결제 시도 이력)가 보인다.
  3. 1만 건 기준 목록 조회가 1초 안에 끝난다.
- 기능 명세서: `docs/fsd/orders/REQ-01-order-search.md`

### REQ-02 결제 실패 건 처리

- 정의: 담당자가 결제 실패 주문을 확인하고 재시도를 요청한다.
- 우선순위: 필수
- 인수 조건:
  1. 결제 실패 주문만 모아 볼 수 있다.
  2. 재시도를 요청하면 주문 상태가 '결제 대기'로 바뀌고 결과가 갱신된다.
- 기능 명세서: `docs/fsd/orders/REQ-02-payment-retry.md`

## 6. 비기능 요구

성능, 보안, 가용성처럼 기능이 아닌 요구를 측정 가능한 값으로 적는다. "빠르게", "안정적으로" 같은 말은 쓰지 않는다.

작성 예:

| 번호 | 항목 | 값 | 측정 방법 |
|---|---|---|---|
| NFR-01 | 사용자 규모 | 동시 사용자 30명 | 부하 테스트 |
| NFR-03 | 주문 생성 처리량 | 초당 10건 | 부하 테스트 |
| NFR-04 | 목록 조회 응답 | 1만 건 기준 1초 이내 | 실측 |
| NFR-05 | 개인정보 | 주문자 연락처는 화면에서 마스킹, 로그에 남기지 않는다 | 코드 리뷰, 로그 검사 |

## 7. 제약과 가정

바꿀 수 없는 조건(제약)과 확인하지 못해 그렇다고 치고 진행하는 것(가정)을 나눠 적는다. 가정은 누가 답하면 확정되는지 적는다.

작성 예:

| 구분 | 내용 | 비고 |
|---|---|---|
| 제약 | 결제 대행사는 현재 계약된 A사 하나 | 계약 기간 2027-03까지 |
| 가정 | 주문 보관 기간은 1년 | 운영팀장 확인 필요 |

## 8. 열린 질문

아직 답을 받지 못한 질문과, 답이 오기 전까지 어떻게 진행하는지 적는다.

작성 예:

| 질문 | 지금 가정 | 누가 답하나 |
|---|---|---|
| 환불도 이 화면에서 처리해야 하나 | 이번 범위에서 제외 | 운영팀장 |

## 9. 추적 표

사용자가 요구한 문장 하나하나가 어느 요구사항에 들어갔는지 적는다. 어느 요구사항에도 들어가지 않은 요구 문장이 있으면 안 된다.

작성 예:

| 사용자 요구 (원문) | 요구사항 | 기능 명세서 |
|---|---|---|
| "결제 실패한 주문을 바로 알고 싶다" | REQ-02 | REQ-02-payment-retry.md |
| "주문을 이름으로 찾고 싶다" | REQ-01 | REQ-01-order-search.md |
