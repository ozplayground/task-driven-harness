# 주제 테스트 케이스

| 항목 | 내용 |
|---|---|
| 대상 요구사항 | |
| 참고 문서 | 이 문서가 근거로 삼은 문서. 링크로 적는다. `[요구사항 정의서](../prd/orders.md)` |

이 문서는 요구사항, 기능, 규칙 하나하나를 어떤 입력으로 어떻게 확인하는지 정한다. 케이스마다 번호(TC-nn)를 붙이고 기대 결과는 통과인지 실패인지 바로 판정할 수 있는 값으로 쓴다. 테스트 코드는 이 번호를 이름에 남긴다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 정상 케이스

기능이 의도대로 동작하는 경우를 적는다. 케이스마다 무엇을 확인하는지(요구사항·기능·규칙 번호), 수준, 시작 전 상태, 단계, 기대 결과, 누가 만드는지.

작성 예:

| 번호 | 대상 | 수준 | 전제 | 단계 | 기대 결과 | 담당 |
|---|---|---|---|---|---|---|
| TC-09 | REQ-02 FN-01 | 통합 | 결제 실패 주문 3건, 결제 완료 주문 2건 | GET /orders?status=payment_failed | 200, items 3건, 모두 status가 payment_failed | I1 |
| TC-10 | REQ-02 FN-02 BR-03 | 통합 | 결제 실패 주문 1건 | POST /orders/{id}/payment-retry | 202, 주문 상태 payment_pending, 큐에 작업 1건 | I1 |
| TC-11 | REQ-02 FN-02 | 화면 | 담당자 로그인, 결제 실패 주문 1건 | 목록에서 재시도 버튼 → MSG-02 확인 → 계속 | 목록에서 그 주문이 사라지고 안내 문구 표시 | I3 |

## 2. 경계와 오류 케이스

잘못된 입력, 한도, 권한 없음, 동시 요청 같은 경우를 적는다. 기대 결과에는 에러 코드와 문구 원문을 쓴다.

작성 예:

| 번호 | 대상 | 입력 | 기대 결과 | 담당 |
|---|---|---|---|---|
| TC-12 | REQ-02 4.4 | 기간 91일 | 422 VALIDATION_FAILED, "조회 기간은 90일까지입니다." | I1 |
| TC-13 | REQ-02 4.6 | 조회 역할로 재시도 요청 | 403 | I1 |
| TC-14 | REQ-02 4.10 | 같은 주문에 재시도 요청 동시 2건 | 하나는 202, 하나는 409 PAYMENT_ALREADY_PENDING | I1 |
| TC-15 | REQ-02 BR-04 | 하루 6번째 재시도 | 409, "재시도는 하루 5회까지입니다." | I1 |
