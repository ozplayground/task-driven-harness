# ADR-000 결정 제목

| 항목 | 내용 |
|---|---|
| 상태 | proposed (제안) / decided (확정) / deferred (미룸) / superseded (대체됨) |
| 확정한 사람 | 사용자 / 구현 에이전트 (승격) / 자동 (위임장 조항) |
| 참고 문서 | 이 문서가 근거로 삼은 문서. 링크로 적는다. `[요구사항 정의서](../prd/orders.md)` |

되돌리기 어려운 결정 하나에 기록 하나를 쓴다. 제목은 무엇을 어떻게 하기로 했는지가 드러나게 짓는다. "저장소 선택"보다 "주문과 결제 시도를 PostgreSQL 하나에 저장한다"가 낫다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 배경

이 결정이 왜 필요해졌는지 두세 문장으로 쓴다. 어떤 요구나 제약이 이 결정을 요구하는지, 관련 수치가 있으면 수치와 출처를 적는다.

작성 예:

> 주문 생성이 초당 10건(NFR-03)인데 결제 대행사 응답이 최대 30초 걸린다. 결제 결과를 요청 안에서 기다리면 API가 막히므로 결제 결과 처리를 요청과 분리해야 한다. 팀은 2명이고 운영할 인프라를 늘리고 싶지 않다(사용자 답, notes 2026-09-18).

## 2. 검토한 대안

대안을 둘 이상 적는다. 대안마다 장점과 단점을 쓰고, 그 장단점의 근거가 어디서 왔는지(조사 문서의 위치, 실측, 공식 문서) 적는다. 대안이 정말 하나뿐이라면 왜 다른 대안이 없는지를 쓴다.

작성 예:

| 대안 | 장점 | 단점 | 근거 |
|---|---|---|---|
| A. PostgreSQL 기반 작업 큐 (procrastinate) | 추가 인프라 없음. 주문 저장과 작업 등록을 한 트랜잭션에 넣을 수 있다 | 처리량 한계가 DB에 묶인다 | docs/research/queue-options.md §3 |
| B. Redis 큐 | 처리량이 높다 | Redis를 하나 더 운영해야 한다. 작업 등록과 주문 저장이 원자적이지 않다 | 같은 문서 §4 |
| C. 결제 대행사 웹훅만 사용 | 큐가 필요 없다 | 웹훅이 유실되면 복구 수단이 없다 | 결제 대행사 API 문서 |

## 3. 판단 기준

무엇을 기준으로 골랐는지 쓴다. 기준은 결정보다 먼저 정해져 있어야 한다. 처리량, 운영 부담, 비용, 되돌리기 비용, 팀의 역량 같은 것들 중 이 결정에 실제로 작용한 것만 적고, 우선순위를 매긴다.

작성 예:

> 1순위는 운영 부담(추가 인프라 없음). 2순위는 주문 저장과 작업 등록의 원자성. 처리량은 초당 10건 수준이라 기준이 되지 않는다.

## 4. 결정

무엇을 하기로 했는지 쓴다. 기술을 고르는 결정이면 버전까지 적고, 왜 그 버전인지도 적는다. 최신 안정판이 아닌 버전을 고른다면 그 이유를 적는다. 추천 단계라면 "추천: A"라고 쓰고 확정은 비워 둔다.

작성 예:

> A를 택한다. procrastinate 3.9(선택 당시 최신 안정판)를 PostgreSQL 18 위에서 쓴다. 운영 부담이 없고, 주문 저장과 작업 등록을 한 트랜잭션에 넣을 수 있어 1·2순위 기준을 모두 만족한다.

## 5. 결과

이 결정 때문에 뒤에서 반드시 해야 하는 것과 할 수 없게 되는 것을 적는다. 후속 설계 문서, 계약, 코드 규칙에 영향을 주는 것을 빠뜨리지 않는다.

작성 예:

> - 작업 형식과 재시도 규칙을 데이터 모델 문서에서 정해야 한다.
> - worker는 procrastinate 워커로 구현한다. 별도 큐 클라이언트를 만들지 않는다.
> - 처리량이 DB에 묶이므로 초당 100건을 넘는 요구가 생기면 이 결정을 다시 본다.

## 6. 다시 볼 조건

어떤 상황이 되면 이 결정을 다시 검토할지 쓴다. 미룬 결정(deferred)이라면 이 절이 본문이다. 무엇이 확인되면 결정할 수 있는지를 적는다.

작성 예:

> 주문 생성이 초당 100건을 넘거나, Redis를 다른 이유로 운영하게 되면 다시 본다.
