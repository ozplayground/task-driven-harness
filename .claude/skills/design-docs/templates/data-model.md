# 데이터 모델

| 항목 | 내용 |
|---|---|
| 저장소 | [아키텍처](architecture.md) 스택 표의 저장소와 버전 |
| 참고 문서 | 이 문서가 근거로 삼은 문서. 링크로 적는다. `[요구사항 정의서](../prd/orders.md)` |

이 문서는 무엇을 어디에 어떤 형태로 저장하는지 정한다. 엔티티마다 필드, 제약, 인덱스를 적고, 얼마나 보관하고 언제 지우는지도 정한다. 구현할 때 스키마와 마이그레이션은 이 문서를 그대로 옮긴 것이어야 한다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 엔티티와 관계

엔티티를 나열하고 서로 어떤 관계인지 적는다. 그림이 있으면 넣고, 없으면 문장으로 쓴다.

작성 예:

> 주문(E-Order) 하나에 주문 항목(E-OrderItem)이 여럿 있다. 주문 하나에 결제 시도(E-PaymentAttempt)가 여럿 있고, 가장 최근 시도의 결과가 주문 상태를 정한다. 사용자(E-User)는 주문을 만들지 않고 조회와 처리만 한다.

## 2. 엔티티 상세

엔티티마다 필드 표를 쓴다. 필드마다 타입, 제약(널 허용, 유일, 외래키, 값 범위), 기본값, 설명. 인덱스는 이름, 대상 열, 어떤 조회를 위한 것인지 적는다. 상태 필드가 있으면 허용되는 값과 전이를 적는다.

### E-Order 주문

| 필드 | 타입 | 제약 | 기본값 | 설명 |
|---|---|---|---|---|
| id | text | PK | `ord_` + 난수 | |
| orderer_name | text | NOT NULL, 50자 | | 주문자 이름 |
| amount | integer | NOT NULL, ≥ 0 | | 원 단위 |
| status | text | NOT NULL, 아래 값 중 하나 | `created` | |
| failed_at | timestamptz | NULL 허용 | | status가 payment_failed로 바뀐 시각 |
| created_at | timestamptz | NOT NULL | now() | |

status 값: `created` → `payment_pending` → `paid` 또는 `payment_failed`. `payment_failed`에서 재시도하면 `payment_pending`으로 돌아간다.

인덱스:

| 이름 | 열 | 용도 |
|---|---|---|
| ix_orders_status_failed_at | (status, failed_at desc) | 결제 실패 목록 조회 |
| ix_orders_orderer_name | orderer_name | 이름 검색 |

### E-PaymentAttempt 결제 시도

(같은 형식으로 쓴다.)

## 3. 저장소 배치

엔티티마다 어느 저장소에 두는지, 왜 그런지 적는다. 저장소가 하나면 그렇다고 쓴다.

작성 예:

> 모든 엔티티는 PostgreSQL 18 하나에 둔다(ADR-003). 큐 테이블(procrastinate)도 같은 DB에 두어 주문 저장과 작업 등록을 한 트랜잭션에 넣는다(ADR-002).

## 4. 대용량과 시계열

데이터가 많이 쌓이는 엔티티가 있으면 어떻게 다룰지 적는다. 파티션, 별도 테이블, 보관 기간 제한 같은 것. 해당 없으면 없다고 쓴다.

작성 예:

> 결제 시도 기록은 하루 5천 건씩 쌓인다. 1년이면 200만 건이라 파티션 없이 인덱스로 충분하다. 100만 건을 넘는 시점에 조회 시간을 다시 잰다.

## 5. 보관과 삭제

엔티티마다 얼마나 보관하고 어떻게 지우는지, 그 근거가 무엇인지 적는다. 개인정보가 있으면 규제 문서(compliance)의 항목을 가리킨다.

작성 예:

| 엔티티 | 보관 기간 | 삭제 방법 | 근거 |
|---|---|---|---|
| 주문 | 1년 | 매일 새벽 배치가 1년 지난 주문을 지운다 | [가정] 운영팀장 확인 필요 |
| 주문자 연락처 | 주문 완료 후 90일 | 필드를 null로 바꾼다 | compliance C-01 |

## 6. 마이그레이션 원칙

스키마를 바꿀 때 지키는 원칙을 적는다. 도구, 되돌리기 가능 여부, 데이터가 있는 상태에서의 변경 방법.

작성 예:

> Alembic으로 관리한다. 모든 마이그레이션은 downgrade를 갖는다. 열을 지울 때는 먼저 쓰기를 멈추는 배포를 하고 다음 배포에서 지운다.

## 7. 대조 표

이 문서가 따르는 결정 기록과, 받아내는 요구사항·기능·규칙을 적는다.

작성 예:

| 따르는 결정 | 받아내는 요구 |
|---|---|
| ADR-003 저장소 | REQ-01 FN-01 주문 조회 (인덱스) |
| ADR-002 큐 | REQ-02 FN-02 재시도 (E-PaymentAttempt) |
