# 테스트 계획

| 항목 | 내용 |
|---|---|
| 대상 | 제품 이름 |
| 참고 문서 | 이 문서가 근거로 삼은 문서. 링크로 적는다. `[요구사항 정의서](../prd/orders.md)` |

이 문서는 무엇을 어떤 수준에서 어떻게 검증할지 정한다. 모든 요구사항과 비기능 요구가 어떤 테스트로 확인되는지, 또는 왜 확인하지 않는지가 드러나야 한다. 개별 테스트 케이스는 테스트 케이스 문서에, 실행 결과는 실행 보고에 쓴다.

각 절 아래의 설명은 무엇을 어떻게 쓰는지에 대한 안내다. 문서를 완성할 때 지운다.

## 1. 범위

검증하는 것과 하지 않는 것을 적는다. 하지 않는 것은 이유를 쓴다.

작성 예:

> 검증: REQ-01~05 전부, NFR-01·03·04·05.
> 제외: NFR-02(데이터 1년 보관)는 시간이 필요해 배치 로직 단위 테스트로 대신한다. 결제 대행사 실제 연동은 계약 계정이 없어 가짜 서버로 대신한다.

## 2. 수준별 방법

단위, 통합, 화면(E2E), 성능, 보안 각 수준에서 무엇을 어떤 도구로 어떤 환경에서 하는지 적는다.

작성 예:

| 수준 | 대상 | 도구 | 환경 |
|---|---|---|---|
| 단위 | core의 상태 전이, 검증 규칙 | pytest | 로컬, 테스트 DB |
| 통합 | API 엔드포인트 전체, 큐 작업 | pytest + 테스트 DB + 가짜 결제 서버 | 로컬 compose |
| 화면 | 로그인부터 재시도 요청까지 주요 흐름 | Playwright, 설치된 Chrome | api·web 실행 |
| 성능 | NFR-03·04 | k6 | 로컬, 1만 건 데이터 |
| 보안 | 권한 표, 연락처 마스킹, 로그 | 통합 테스트에 포함 | |

## 3. 환경

테스트를 돌리는 환경의 구성 요소와 버전을 적는다. 아키텍처 문서의 스택과 같아야 한다.

작성 예:

| 구성 | 값 |
|---|---|
| Python | 3.13 |
| PostgreSQL | 18 (Docker `postgres:18-alpine`) |
| 브라우저 | Chrome 안정판 |
| 결제 대행사 | 로컬 가짜 서버 `tests/fakes/payment.py` |

## 4. 테스트 데이터

데이터를 어디서 가져오거나 어떻게 만드는지 적는다. 개인정보가 들어가면 안 된다.

작성 예:

> 주문 데이터는 `tests/fixtures/orders.py`의 생성기로 만든다. 이름과 연락처는 가짜 값이다. 성능 테스트용 1만 건은 같은 생성기로 시드 42로 만든다.

## 5. 통과 기준

전체 테스트가 통과했다고 볼 조건을 적는다.

작성 예:

> 단위·통합·화면 테스트 실패 0. 성능 테스트가 NFR 값을 만족. 알려진 실패는 실행 보고에 이유와 함께 적혀 있어야 한다.

## 6. 비기능 요구 검증

비기능 요구마다 어떻게 재고 기준값이 무엇인지 적는다.

작성 예:

| 요구 | 측정 방법 | 기준값 | 케이스 |
|---|---|---|---|
| NFR-03 처리량 | k6로 60초 동안 주문 생성 요청 | 초당 10건, 오류 0 | TC-40 |
| NFR-04 목록 조회 | 1만 건에서 GET /orders 100회 | p95 1초 이내 | TC-41 |

## 7. 추적

요구사항과 비기능 요구마다 어느 테스트 케이스가 확인하는지, 누가 만드는지 적는다. 빠진 요구가 있으면 안 된다.

작성 예:

| 요구 | 케이스 | 담당 task |
|---|---|---|
| REQ-01 | TC-01~08 | I1 |
| REQ-02 | TC-09~15 | I1, I2 |
| NFR-02 | 제외 — 배치 단위 테스트 TC-30으로 대신 | I2 |
