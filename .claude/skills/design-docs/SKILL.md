# design-docs — 문서 표준

이 스킬은 문서의 **위치·이름·머리말·참조**와 **골격**(문서마다 반드시 있어야 하는 절)을 정한다. 각 절에 무엇을 쓸지는 정하지 않는다.

## 두 뿌리

| 뿌리 | 무엇 | 수명 | 누가 읽나 |
|---|---|---|---|
| `docs/` | 사용자가 받는 산출물과 결정 기록 | 프로젝트와 같이 | 사용자, 뒤 task, 다음 run, 다른 하네스·사람 |
| `_tasks/<run>/` | 이 run의 진행 기록 | run | 리더, 에이전트, 재개 |

**서브에이전트는 자기 task에 맞는 문서를 이 표에서 고른다.** 브리프가 문서 이름을 부르면 위치는 여기서 찾는다. 표에 없는 문서가 필요하면 만들지 말고 보고서의 "다음에 필요한 것"에 적는다 — 종류를 늘리는 건 리더가 사용자 확인 뒤 이 표를 고쳐서 한다.

## 이름

- kebab-case 영문. 주제 하나. `orders.md`, `wearable-sync.md`
- 같은 주제는 종류 사이에서 같은 이름을 쓴다. `prd/orders.md` → `fsd/orders/REQ-03-checkout.md` → `api/orders.md`. `orders`로 전부 찾힌다
- FSD 파일명은 `REQ-nn-<주제>.md`. REQ 번호가 PRD와 같아야 한다
- 쪼개야 하면 `orders-sync.md`처럼 주제-하위주제
- 결정 기록은 세 자리 번호 + 주제. `decisions/004-activity-storage.md`. 번호는 만든 순서, 재사용 안 함
- 하네스 내부 파일은 task ID·라운드가 이름

## 머리말 — 모든 `docs/` 문서 공통

```yaml
---
kind: fsd                  # 디렉토리와 같음
run: order-page            # 만든 run
task: T1                   # 만든 task
status: draft              # draft → reviewed (리뷰어 confirmed 뒤 리더가 바꿈)
inputs:                    # 이 문서가 근거로 삼은 문서. 체인의 고리
  - docs/prd/orders.md
updated: 2026-09-17
---
```

결정 기록은 `status: proposed | decided | deferred | superseded`와 `decided_by: user | executor`를 추가로 갖는다.

`inputs`가 체인이다. 어느 파일에서 시작해도 `inputs`를 거슬러 올라가면 요구까지 닿아야 한다. `grep -rl "run: order-page" docs/`로 원장 없이 그 run이 만든 문서가 나온다.

## 참조

- 문서끼리는 저장소 루트 기준 상대 경로
- 항목은 ID로. `docs/prd/orders.md#REQ-03`, `docs/fsd/orders/REQ-03-checkout.md#FN-02`, `docs/api/orders.md §2.1`, `ADR-004`, `TC-12`
- ID 체계: 요구 `REQ-nn`·`NFR-nn`(PRD), FSD 안의 기능 `FN-nn`, 화면 `SCR-nn`·구성 요소 `SCR-nn-Enn`·규칙 `BR-nn`·메시지 `MSG-nn`(파일 안에서 번호, 문서 밖에서는 `REQ-03 FN-02`, `REQ-03 BR-04`), 결정 `ADR-nnn`, 엔티티 `E-<이름>`, compliance `C-nn`, 테스트 `TC-nn`, 비판 `P-Cn`, finding `<task>-Fn`

리뷰어와 critic은 이 참조를 따라가 대조한다. 참조 없는 주장은 대조할 수 없다.

## 저장소 관례가 위

저장소에 이미 문서 규칙이 있으면(`documentation/`, ADR 디렉토리, 다른 머리말) 그것을 따르고 `notes.md`와 `docs/README.md`에 대응을 적는다. 이 표준은 관례가 없을 때의 기본값이다.

## 골격

설계 문서의 검증은 대조다. 위로는 architecture·ADR을 어기지 않는가, 아래로는 PRD의 REQ와 FSD의 기능·규칙을 받아내는가. 문서 끝에 **대조 표**(따르는 ADR / 받아내는 REQ·FN·BR)를 붙인다. 빈 곳은 `[가정]`(되돌릴 수 있음) 또는 `[결정 필요]`(되돌리기 어려움 → 막힌 것으로 보고). "해당 없음"도 적는다 — 빈칸은 잊은 것과 구분되지 않는다.

| 문서 | 답하는 질문 | 최소 절 | ID |
|---|---|---|---|
| PRD `prd/<제품>.md` | 무엇을 요구하는가 — 요구사항 정의서 | 배경·문제, 목표·측정, 대상 사용자·역할, 범위(포함/제외), **요구사항 목록**(REQ마다: 이름, 정의 — 무엇을·누가·어디까지, 우선순위, 인수 조건, FSD 경로), 비기능 요구(측정 가능한 값), 제약·가정, 열린 질문, **추적 표**(사용자 요구 → REQ → FSD) | `REQ-nn`, `NFR-nn` |
| FSD `fsd/<제품>/REQ-nn-<주제>.md` | 요구사항 하나를 이루는 기능이 정확히 어떻게 동작하나 — 구현자가 추측할 것이 없는 수준 | **문서 머리**: 상세화하는 REQ와 PRD 정의·인수 조건 인용, 기능 목록(FN마다 이름·한 줄 정의·받는 인수 조건), 사용 역할, 선행 조건. **기능(FN)마다**: ① 화면 목록(화면 ID, 이름, 진입 경로, 이동 관계, 권한) ② 화면별 상세(영역 구성, 구성 요소 표 — 요소 ID·종류·라벨·기본값·필수·입력 제약·표시 조건·동작, 목록이면 컬럼·정렬·필터·검색·페이지, 상태 — 로딩·빈·오류·권한 없음) ③ 기능 흐름(정상·대안·예외 단계, 상태 전이) ④ 비즈니스 규칙 ⑤ 입력 검증(필드별 규칙, 검증 시점 — 화면·서버, 오류 문구 원문) ⑥ 처리 로직(동작별 전후 조건·부수 효과) ⑦ 권한(동작 × 역할 표) ⑧ 메시지(확인·알림·안내 문구 원문) ⑨ 데이터(읽고 쓰는 엔티티·필드) ⑩ 연동(호출하는 API) ⑪ 예외·경계(동시 편집, 한도, 타임아웃, 사라진 참조). **문서 끝**: 추적(REQ 인수 조건 → FN·절), 미결·가정 | `FN-nn`, `SCR-nn`, `SCR-nn-Enn`, `BR-nn`, `MSG-nn` |
| 데이터 모델 `design/data-model.md` | 무엇을 어디에 어떤 형태로 | 엔티티·관계, 엔티티별 필드·제약·인덱스, 저장소 배치(ADR 링크), 시계열·대용량 전략, 보존·삭제(compliance 링크), 마이그레이션 원칙 | `E-<이름>` |
| 흐름 설계 `design/<주제>.md` | 이 흐름이 정확히 어떻게 도나 | 트리거, 참여 모듈, 시퀀스, 실패·재시도·멱등성, 상태, 경계 조건, 관측 | 단계 번호 |
| compliance `compliance/<주제>.md` | 어떤 데이터가 어떤 규제·심사 대상이고 무엇을 지켜야 하나 | 대상 데이터 분류, 적용 규제·스토어 요건, 동의·고지, 보존·삭제·이전, 접근 통제, 설계에 강제되는 항목 | `C-nn` |
| 테스트 계획 `qa/test-plan.md` | 무엇을 어떤 수준에서 어떻게 검증하나 | 범위·제외, 수준별 전략(단위·통합·E2E·성능·보안), 환경, 테스트 데이터 출처, 완료 기준, NFR 검증 방법 | — |
| 테스트 케이스 `qa/<주제>.md` | 각 REQ·FN·BR을 어떤 입력으로 확인하나 | REQ·FN·BR ↔ 케이스 표, 전제, 단계, 기대 결과, 경계·오류 | `TC-nn` |
| 테스트 실행 보고 `qa/report-<날짜>.md` | 무엇을 돌렸고 결과가 무엇인가 | 실행 범위, TC별 결과, 실패 재현, 미실행과 이유 | — |
| 배포 `ops/deployment.md` | 어디에 어떻게 올리고 되돌리나 | 환경 표, 인프라 구성(IaC 위치), 배포 절차, 마이그레이션 순서, 롤백 조건·절차, 시크릿 목록(값 아님) | — |
| 모니터링 `ops/monitoring.md` | 무엇을 보고 언제 깨우나 | 지표(무엇·어디서), 알람 조건, 대시보드 위치, 로그 조회 | — |
| 런북 `ops/runbook.md` | 장애 시 무엇을 하나 | 증상별: 확인 → 조치 → 확인, 에스컬레이션 | — |

## 종료 시 승격 — 리더가 한다

| `_tasks/`의 것 | 어디로 |
|---|---|
| 실행자 보고의 "명세에 없어 내가 정한 것" 중 되돌리기 어려운 것 | 새 ADR (`decided_by: executor`, 사용자 확인 표시) |
| 같은 것 중 되돌릴 수 있는 것 | 해당 FSD·design 문서에 `[가정]` 항목 |
| 리뷰의 waive | run 보고서 §알고 넘긴 것 |
| 미검증 항목 | run 보고서 §미검증 |
| 요청 밖 발견 | run 보고서 §다음에 할 것 |
| 비판 항목의 기각 이유 | run 보고서 §결정 경위 |

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 다음 run이 "왜 이렇게 돼 있지" | 가정이 보고서에서 죽음. 승격 안 함 |
| 같은 주제 문서가 두 곳에 | 이름 규칙 무시 |
| critic이 "이 결정 근거가 어디?" | `inputs` 비어 있음 |
| 구현자가 "데이터 모델에 없는 필드를 만들었다" | 대조 표 없음 |
| compliance가 설계 뒤에 나옴 | 보존·삭제가 데이터 모델을 바꾼다. 먼저다 |
| 스킬마다 다른 경로 | 위치는 여기만. 다른 스킬은 문서 위치를 정하지 않는다 |
| PRD와 FSD가 한 파일, 또는 제품 전체를 담은 FSD 하나 | 문서 종류를 섞음. PRD 하나 + REQ마다 FSD 하나, FSD 안은 기능(FN)별 |
| FSD가 요구사항 목록 수준이라 구현자가 화면·문구·기본값을 정함 | FSD 골격 절을 비워 둠. 빈 절은 "해당 없음 — 이유" |
| REQ에 FSD가 없거나 FSD가 어느 REQ인지 모름 | PRD 추적 표와 FSD 머리의 REQ 인용이 없음 |
| FSD가 요구사항을 기능으로 나누지 않고 요구사항 문장을 그대로 상세화함 | 기능 목록(FN)을 정하지 않음. 인수 조건이 어느 FN에 걸리는지 추적 표가 없음 |
