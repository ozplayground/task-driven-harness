# git-workflow — 요구할 때만 하고, 되돌릴 수 없는 것은 사람이 한다

## 하는 것과 안 하는 것

| 리더·실행자가 한다 | 사용자만 한다 |
|---|---|
| 브랜치 생성, 커밋 | 머지, 푸시, 태그, 릴리스 |
| PR 생성 (요구 시, 푸시는 사용자 확인 후) | force push, rebase, amend, reset --hard, 히스토리 재작성 |
| 상태 조회, diff, log | 브랜치 삭제 |

## task와 브랜치

요구가 있으면 run마다 브랜치 하나가 기본이다. `task/<run>`. task별 브랜치는 사용자가 원할 때만 `task/<run>/<id>`.

브리프가 커밋을 요구하면 실행자는 자기 소유 경로만 `git add`한다. `git add .`나 `git add -A`는 쓰지 않는다. 소유 경로 밖이 스테이징되면 그 자체가 위반 신호다.

## 커밋

- task 하나가 done이 될 때 커밋 하나가 기본. 실행자가 중간 커밋을 하려면 브리프에 허용이 있어야 한다.
- 메시지 첫 줄: `<type>: <무엇을>` 50자 이내. type은 저장소 관례를 따르고, 없으면 `feat fix docs test refactor chore`.
- 본문에 task를 남긴다.

  ```
  feat: 주문 목록·생성 API

  Task: order-page/T2
  ```

  `git log --grep="Task: order-page"`로 그 run의 커밋을 찾는다.
- 실패한 task의 부분 산출물도 보존이 필요하면 커밋한다. 메시지에 `wip:` 접두어와 상태.

## 머지·PR 요구 시

- PR은 만들 수 있다. 본문에 run의 최종 보고(요구 대비 결과, 가정, 요청 밖 발견, 미검증)를 넣는다.
- 푸시 전에 사용자에게 대상 원격·브랜치를 확인한다.
- 머지는 하지 않는다. "머지해줘"라고 해도 되돌릴 수 없으므로 명령을 보여주고 사용자가 실행한다. 사용자가 그래도 하라고 재확인하면 한다.

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 한 커밋에 두 task의 변경 | `git add .` |
| 실행자 둘이 같은 브랜치에서 충돌 | 소유 경로가 겹침. 원장 validate로 돌아갈 것 |
| 히스토리가 사라짐 | amend·rebase·reset을 실행자가 함 |
| 원장과 커밋이 다름 | 커밋 푸터 누락. 푸터가 정본이다 |
