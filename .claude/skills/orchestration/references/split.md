# 분할 — 요구를 task로 나누는 규칙

리더가 요구(wanted)·결손·아키텍트의 후속 필수 설계를 아래 규칙으로 task로 나눈다. 모듈 경계와 데이터 소유권은 구조 문서를 따른다. 구조 문서가 없고 경계가 갈리면 아키텍트에게 묻는다.

task는 **한 실행자가 한 번 호출로 끝낼 수 있고, 끝났는지를 산출물로 확인할 수 있는 단위**다. 이 두 조건을 만족하는 가장 큰 덩어리가 좋은 task다.

## 규칙

### 1. 산출물 하나에 task 하나

task의 완료 기준은 "무엇이 존재하고 무엇을 통과하는가"로 적을 수 있어야 한다. "잘 만든다", "적절히 처리한다"는 완료 기준이 아니다.

```
좋음: src/api/orders/** 에 GET /orders, POST /orders 구현. tests/api/orders.test.ts 통과
좋음: docs/spec/orders-fsd.md 에 화면 4개의 동작·검증·에러·권한 정의. 결손 보고 없음
나쁨: 주문 기능 백엔드
```

구현과 그 구현의 테스트는 **한 task**다.

**코드 task의 완료 기준에는 리더가 한 줄을 자동으로 붙인다:** "구조 문서의 횡단 규약과 코드 규칙 준수".

### 2. 소유 경로가 겹치지 않게

동시에 돌 수 있는 두 task는 같은 파일을 만지면 안 된다. `ledger.py validate`가 이걸 검사한다. 겹치면 셋 중 하나를 고른다.

- 의존을 건다 (순차)
- 경로를 더 잘게 가른다 (`src/api/**` → `src/api/orders/**`, `src/api/payments/**`)
- 겹치는 부분을 선행 task로 뺀다 (아래 3번)

경로는 glob으로 적는다. 디렉토리는 `**`로 끝낸다. 파일 하나면 그 경로 그대로.

### 3. 공유 자원은 선행 task

둘 이상의 task가 참조하는 것은 그것을 만드는 task를 먼저 둔다.

| 공유 자원 | 선행 task의 산출물 |
|---|---|
| 화면과 API가 주고받는 데이터 | 교환 규격 문서 |
| 여러 모듈이 쓰는 타입·상수·유틸 | 그 파일들 |
| 데이터베이스 스키마 | 스키마 정의 + 마이그레이션 |
| 에러 코드 | 에러 카탈로그 |

선행 task는 문서일 때가 많다. 문서 task도 완료 기준과 리뷰를 거친다.

### 4. 하나의 통찰을 공유하면 쪼개지 않는다

알고리즘 하나, 마이그레이션 하나, 미묘한 버그 하나는 통째로 한 task다. "파일이 여러 개라서" 쪼개면 안 된다. 반대로 서로 독립인 엔드포인트 셋은 셋으로 쪼개도 된다. 쪼갤지 판단하는 질문은 하나다. **한쪽을 만드는 사람이 다른 쪽의 내부를 알아야 하는가?** 알아야 하면 한 task.

### 5. 의존은 입력 의존과 파일 충돌뿐

"먼저 하는 게 자연스러워서"는 의존이 아니다. 의존을 거는 이유는 둘뿐이다.

- **입력 의존:** B가 A의 산출물을 읽어야 한다
- **파일 충돌:** A와 B가 같은 경로를 만진다

그 외에는 의존을 걸지 않는다. 의존이 없으면 동시에 돈다. 병렬 개수는 적지 않는다.

### 6. 문서와 코드는 다른 task

"명세를 쓰고 그대로 구현"은 두 task다. 문서 task가 done이 되어야 코드 task의 입력이 확정된다.

### 7. 크기 감각

| 신호 | 판단 |
|---|---|
| 완료 기준이 5개를 넘는다 | 두 task일 가능성 |
| 소유 경로가 서로 무관한 디렉토리 셋 이상 | 두 task일 가능성 |
| 완료 기준이 하나뿐이고 파일이 하나 | 직접 모드 후보 |
| task 수가 8개를 넘는다 | 요구가 하나가 아니다. 사용자와 run을 나눌지 상의 |

## 승인 요청 형식

```
run: order-page
요구: 주문 조회 화면과 주문 API

| id | 제목 | 종류 | 소유 경로 | 의존 | 완료 기준 |
|---|---|---|---|---|---|
| T1 | 주문 교환 규격 | doc | <계약 문서 경로> | - | GET/POST /orders 요청·응답·에러 정의 |
| T2 | 주문 API | code | src/api/orders/**, tests/api/orders.* | T1 | T1 규격대로 동작, 테스트 통과, 규약 준수 |
| T3 | 주문 화면 | code | src/pages/orders/**, src/components/orders/** | T1 | 목록·상세 렌더, T1 규격으로 호출, 규약 준수 |

결정 (되돌리기 어려움 — 하나 고르세요):
  ADR-002 활동 샘플 저장소 — A Postgres 파티션 (추천) / B Timescale. 근거: <조사 결과 경로>
비판 요약: P-C1 반영 (T3 기준에 FR-07 추가), P-C2 기각 (이유)
가정: 목 데이터는 T3 안에서 T1 규격으로 만든다
질문: 없음

이대로 진행할까요?
```

사용자가 고치면 반영하고 다시 보여준다. "그냥 해"도 승인이다.

## 흔한 실패

| 증상 | 원인 |
|---|---|
| 두 실행자가 같은 파일을 서로 덮어씀 | 경로를 `src/**`처럼 넓게 잡고 validate를 건너뜀 |
| 화면이 API와 다른 필드명을 씀 | 교환 규격을 선행 task로 빼지 않음 |
| 리뷰가 "구현은 맞는데 명세가 틀림"을 냄 | 문서와 코드를 한 task에 넣음 |
| task 12개, 리뷰 12회, 정작 요구는 화면 하나 | 파일 단위로 쪼갬. 산출물 단위로 다시 묶을 것 |
| 실행자가 "이걸 하려면 저 모듈도 고쳐야" 보고 | 공유 자원을 못 봄. 그 모듈을 선행 task로 추가 (사용자 승인) |
| 실행자가 "막힌 것: 입력 없음" 보고 | 선행 문서 누락. 그 문서를 만드는 task를 추가하고 의존을 건다 (사용자 확인). 구조에 닿으면 아키텍트 상담 |
| task 경계가 모듈 경계와 어긋남 | 구조 문서를 안 보고 나눔. 한 task가 두 모듈의 데이터를 쓰면 다시 나눌 것 |
