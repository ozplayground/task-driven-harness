# 브리프 — 서브에이전트에게 넘기는 프롬프트

서브에이전트는 이 브리프와 자기 정의 파일, preload된 스킬 외에 아무것도 모른다. 리더의 대화 맥락은 넘어가지 않는다. 길이가 아니라 **결정된 것과 결정되지 않은 것의 경계**가 명확해야 한다.

모든 호출은 `Agent` 도구, `subagent_type`은 원장의 `agent`, `run_in_background: true`. 스킬은 브리프가 지정하지 않는다. 에이전트 정의에 있다. 문서의 위치·이름도 브리프가 정하지 않는다. 브리프가 주는 것은 **입력 문서의 경로**(이미 존재하는 것)와 **소유 경로**(쓸 수 있는 곳)다. 문서 내용을 브리프에 옮기지 않는다. 읽을 범위는 절 단위로 좁혀 준다("FSD REQ-03", "계약 §2").

`ledger.py brief <id>`가 완료 기준, 경로, 의존 task의 산출물·보고서 경로, 대상 task의 open finding, 워크트리 경로를 뽑는다. 그것을 아래 형식에 옮긴다.

모든 브리프의 EXPECTED OUTCOME 마지막 줄은 같다. **보고에 "다음에 필요한 것" 절을 넣는다.**

## 산출물 브리프 (researcher, spec-writer, ux-designer, contract-designer, security 요건, backend-developer, frontend-developer, devops, verifier)

```
## TASK
run: <run>  task: <id>  제목: <제목>
<한 문단. 무엇을 만드는가>

## EXPECTED OUTCOME
- <완료 기준 — 원장의 acceptance 그대로>
- 보고에 "다음에 필요한 것" 절

## PATHS
작업 트리: <.worktrees/<task> 절대 경로> (브랜치 feature/<run>/<task>). 이 안에서만 일한다
소유: <경로 목록>
이 밖은 읽기만 한다. 밖을 바꿔야 완료된다면 멈추고 보고한다.

## MUST DO
- 입력 문서: <경로와 읽을 절>. 있으면 그대로 따른다. 없는 것은 요청에서 읽는다
- 입력이어야 하는 문서가 없으면 만들지 않는다. 시작 전에 "막힌 것: 입력 없음"으로 보고
- <이 task 고유의 필수 사항>
- 작업 트리 안에서 산출물마다 커밋한다. switch·merge·push는 하지 않는다. 마지막 커밋 해시를 보고서에

## MUST NOT DO
- 요청 밖 수정. 관련 있는 버그는 task-execution의 "발견한 버그" 절대로
- 소유 경로 밖 수정
- 테스트를 조건에 맞게 고쳐 통과시키기
- 실패한 작업을 되돌리기
- <이 task 고유의 금지>

## CONTEXT
- 문서: <구조 문서·코드 규칙·로컬 실행 문서 경로. 있는 것만>
- 결정된 것: <notes의 관련 결정과 가정>
- 관련 task: <선행 task의 산출물 경로>
```

조사 task는 TASK에 닫힌 질문(또는 비교 대상과 목적)과 결정 기준·NFR 문서 경로를 넣는다.

## 재작업 브리프 (원래 task와 같은 에이전트)

산출물 브리프와 같되 TASK에 `round: <n>`, PATHS의 작업 트리는 **대상 task의 워크트리**, CONTEXT에 다음을 넣는다.

```
- 재작업: round <n>. 고칠 finding: <ID 목록>. 이 ID들만 고친다. 리뷰 파일: <경로>
```

리뷰 내용을 요약해 옮기지 않는다. 원래 인스턴스가 살아 있으면 새 브리프 대신 `SendMessage`로 같은 내용을 준다.

## architect 브리프 — 첫 호출

```
## TASK
run: <run>  구조 결정 — 첫 호출
이 요구에 어떤 구조 결정이 걸려 있는지, 정하려면 무엇을 조사해야 하는지 답한다. 결정하지 않는다.

## INPUTS
- 받은 것: <given 목록과 경로>
- 요구: <wanted>
- 결손과 답: <notes의 관련 항목>
- 보안 요건: <docs/design/security.md, 있으면>
- 저장소 상태: <기존 구조 문서·결정 기록 경로, 없으면 "없음">
- 리더가 본 결정 지점: <스택 / 저장소 / 통신 / 모듈 경계 중 무엇이 걸려 있다고 보는가>

## EXPECTED OUTCOME
- 기존 구조 문서·결정 기록이 이번 요구를 덮는 부분과 덮지 못하는 부분
- 정해야 할 결정과 조사 목록 (질문 하나에 조사 하나)
- 요구에 없는 NFR·제약 (유인: 사용자 질문으로, 무인: 조사 항목으로)
- 다음에 필요한 것

## MUST NOT DO
- 결정하기. 코드·명세·계약 쓰기. 기억으로 조사를 대신하기. task를 나누기
```

**결정 초안 (SendMessage, 같은 인스턴스):** "조사가 끝났다. 결과: <경로 목록>. 사용자 답: <NFR·제약>. 결정 사슬 순서로 결정 기록 초안과 구조 문서 초안을 쓰고, 후속 필수 설계 목록을 보고해라. 확정하지 마라."

**비판 반영 (SendMessage):** "비판 파일 <경로>의 <ID 목록>을 다뤄라. 반박은 근거와 함께."

**상담 (SendMessage):** "<task id>가 "<막힌 것 원문>"으로 막혔다. 구조 문서·결정 기록 안에서 답하고, 구조 변경이 필요하면 결정 기록 추가를 제안해라."

## 리뷰 브리프 (doc-reviewer, code-reviewer, security 검토)

```
## TASK
run: <run>  task: <id>  대상: <target>  round: <n>
<target>의 산출물이 완료 기준을 만족하는지 판정한다. (security면: 보안 관점으로 검토한다)

## INPUTS
- 완료 기준: <target의 acceptance 목록>
- 소유 경로: <target의 경로 목록>. 작업 트리: <.worktrees/<target>>, 기준선 feature/<run>
- 작성자 보고: <target의 report 경로>
- 입력 문서: <명세·계약·구조·보안 요건 문서 경로>
- 이전 라운드 리뷰: <있으면 경로> 와 finding 목록 <ID: 상태>

## EXPECTED OUTCOME
리뷰 파일 <경로>. verdict 는 confirmed / needs-fix / inconclusive 중 하나. finding마다 ID·심각도·위치·내용·재현.

## MUST DO
- 완료 기준 하나하나를 산출물에서 직접 확인한다. 보고문을 근거로 쓰지 않는다
- 코드면 테스트·빌드를 직접 실행하고 3-dot diff로 범위를 본다. 문서면 템플릿 절과 입력 문서 항목을 대조한다
- round 2 이상이면 이전 finding의 해소 여부를 ID별로 적고, 새 finding은 회귀나 blocker만

## MUST NOT DO
- 산출물을 고치지 않는다. 리뷰 파일 외에 쓰지 않는다
- 완료 기준에 없는 것을 blocker로 올리지 않는다
```

## critic 브리프

```
## TASK
run: <run>  task: <id>  대상: <target 문서 경로 또는 "계획">  round: <n>
문서 비평: <경로>의 내용을 비평한다. / 계획 비판: 구현 투입 전 계획을 비판한다.

## INPUTS
- 대상 문서: <경로> (문서 비평일 때)
- 그 문서의 입력 문서: <문서 정보 표의 참고 문서 경로들>
- 요구: <wanted, PRD 경로>
- 원장: <경로> (계획 비판일 때)
- 조사 결과: <경로 목록>
- 이전 라운드: <있으면 경로> 와 항목 <ID: 상태>

## EXPECTED OUTCOME
비판 파일 <경로>. 항목마다 번호·종류·심각도·대상·내용·확인 방법. 결론(무이의 / 이의 있음과 번호).

## MUST DO
- 문서 원문을 처음부터 끝까지 읽는다
- 기술 스택·버전·수치·규칙마다 이유가 있는지, 요구에 비해 과하거나 필요 없는 것이 없는지, 빠진 것이 없는지 본다

## MUST NOT DO
- 문서·계획 수정. 사용자가 결정한 것 재론. round 2에 새 major·minor
```

## investigator 브리프 (누구나)

```
## QUESTION
<한 문장으로 닫히는 질문>

## SCOPE
읽을 곳: <경로·URL>. 이 밖은 보지 않는다. 읽기 전용.

## EXPECTED OUTCOME
- 답 (파일:줄 근거 포함)
- 확인하지 못한 것
- 200줄 이내
```

## 브리프를 쓸 때

- 완료 기준은 원장의 문장을 **그대로** 옮긴다.
- CONTEXT의 "결정된 것"은 이 task와 관련된 것만.
- 재작업·비판 반영에는 파일 경로와 ID만. 요약하지 않는다.
- "빠르게", "간단히" 같은 말을 넣지 않는다.

## 재개 메시지 (중단된 에이전트를 되살릴 때 — 기본 경로)

죽은 에이전트는 `SendMessage`로 되살아난다. 자기 컨텍스트를 그대로 들고 온다. 원래 브리프를 다시 쓰지 않는다.

```
<중단 사유가 해소됐다는 사실>. 중단된 <task>를 이어서 진행해라.

너는 직전에 "<마지막 보고 문장>"이라고 하고 끊겼다. 원래 브리프의 완료 기준과 MUST DO가 그대로 유효하다.

이어서 할 것:
1. <중단 지점에서 이어지는 작업>

환경 변화:
- <다른 task가 만든 새 파일, 새로 깨진 것, 여전히 깨져 있는 것>

기존 제약 유지: <핵심 금지 사항 한 줄>
```

## 재개 브리프 (새 인스턴스로 다시 던질 때 — 마지막 수단)

산출물 브리프의 절을 그대로 쓰되, TASK 절 제목에 "**중단 재개**"를 적고 두 블록을 끼운다.

```
## TASK
run: <run>  task: <id>  제목: <제목> — **중단 재개**
**이 task는 이전에 중단됐다. 이미 만든 것이 디스크에 있다. 지우고 새로 시작하지 마라.**

## 지금 상태 (리더가 직접 확인, <시각>)
이미 있다: <파일 목록>
<테스트·빌드 결과>
<깨진 것이 있으면 구체적으로>
중단 직전 "<마지막 보고 문장>"이라고 적었다.
**첫 작업은 <무엇>이다.**
```

MUST DO 첫 항목은 "먼저 이미 있는 코드와 보고서의 `## 진행 상태`를 읽고 무엇이 남았는지 스스로 판단해라". MUST NOT DO 첫 항목은 "이미 만든 파일을 지우고 새로 시작하기". 파일 목록과 깨진 지점은 리더가 직접 셸로 확인한 것이어야 한다.
