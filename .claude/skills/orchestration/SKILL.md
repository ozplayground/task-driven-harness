# orchestration — 분석하고, 계획하고, 분배하고, 판정한다

이 스킬은 리더(메인 세션)가 쓴다. 리더는 사용자의 요청을 받아 **분석**하고, task로 나눠 **계획**을 세우고, 각 task를 서브에이전트에 **분배**하고, 보고와 산출물로 **완료를 판정**한다. 산출물을 직접 만들지는 않는다.

- **단위는 task다.** 역할은 task의 속성이고, 순서는 task 간 의존이다. 고정된 단계는 없다.
- **시킨 것만 한다.** 범위를 넓히는 모든 결정은 사용자에게 돌아간다.
- **완료는 보고가 아니라 산출물로 판정한다.**
- **계획은 검증을 받는다.** 구현 투입 전에 critic이 계획을 비판하고, 사용자가 승인한다.
- **판단은 기록한다.** 계획·호출의 근거를 원장 log에 `--because`로 남긴다.

## 실행 모드

`Agent` 도구로 서브에이전트를 던지고 결과를 받는 **팬아웃** 방식이다. 팀 구성이나 팀원 간 통신은 쓰지 않는다. 서로 소통이 필요해 보이면 그 소통 내용을 선행 task(계약 문서)로 뺀다.

| 에이전트 | 역할 | 쓰기 | 다른 에이전트 호출 |
|---|---|---|---|
| 리더(이 세션) | 분석·계획·분배·판정·게이트 | 원장·notes·run 보고서 | 아래 전부 |
| `architect` | 구조·스택·횡단 규약 결정 초안, 후속 필수 설계 목록, 실행 중 구조 상담 | 구조·결정 문서, 자기 보고서 | investigator |
| `executor` | 조사·기획·설계·구현 — 스킬로 역할이 정해짐 | 자기 소유 경로, 자기 보고서 | investigator |
| `reviewer` | 완료 기준 대비 판정 | 리뷰 파일 | investigator |
| `critic` | 구현 투입 전 계획 비판 | 비판 파일 | investigator |
| `investigator` | 질문 하나에 근거 있는 답 | 없음 | 없음 |

**쓰는 task는 리더만 만들고, 읽는 task는 누구나 만든다.**

모든 `Agent` 호출은 `run_in_background: true`로 던지고 알림을 받는다. 같은 `subagent_type`을 여러 번 호출하면 독립 인스턴스가 뜬다. 병렬 개수는 정하지 않는다. 의존이 풀린 것을 한 번에 던지고, 생성이 거부되면 그 task는 `ready`에 남겨 다음 순환에서 다시 던진다.

## 상태는 파일에 둔다

진행 상태를 대화 컨텍스트에 두지 않는다.

원장 조작은 전부 `scripts/ledger.py`로 한다. 손으로 JSON을 고치지 않는다.

```bash
L=.claude/skills/orchestration/scripts/ledger.py
python3 $L init <run> --request "..."
python3 $L add <run> T1 --title "..." --paths "src/a/**" --depends T0 --kind code|doc|research --accept "기준" --because "요구 wanted 2 / 계약 결손 G2"
python3 $L validate <run>     # 의존 사이클, 동시 실행 가능 task 간 경로 겹침
python3 $L approve <run>      # 사용자 승인을 받은 뒤에만. 승인 전에는 research task만 ready가 된다
python3 $L ready <run>        # 지금 던질 수 있는 task
python3 $L set <run> T1 running|review|rework|done|failed|blocked --because "..."
python3 $L finding <run> T1 add T1-F1 blocker "내용"
python3 $L show <run>
```

`--because`가 판단의 근거다. "어느 요구 / 어느 결손 / 어느 보고의 어느 줄 때문에".

`<run>`은 요청을 나타내는 짧은 kebab-case slug다. 한 번 정하면 바꾸지 않는다.

## 흐름

### 0. 컨텍스트 확인

- 미완료 run이 있고 사용자 요청이 그 연장이면 **재개**한다. `ledger.py show`로 상태를 읽고 4단계부터 이어간다.
- 사용자가 특정 task를 지목하면("T3만 다시") 그 task와 그에 의존하는 task를 `ready`로 되돌리고 재실행한다.
- 새 요청이면 새 run이다. 기존 run은 그대로 둔다. 이전 run의 run 보고서가 있으면 먼저 읽는다.

### 1. 분석 — 받은 것과 요구

요청에서 두 가지를 분리한다.

- **받은 것(given):** 첨부 문서, 지목된 파일, 기존 코드, 구두 설명
- **요구(wanted):** 최종적으로 무엇이 있어야 끝나는가

받은 문서가 있으면 `references/intake.md`의 절차로 적재한다. 길면 `investigator`에게 위임한다. **빠진 것을 채우지 않고 목록으로 올린다.**

결손은 세 종류다. **결정**(되돌리기 어려운 것)은 사용자에게 묻고 답 없이 진행하지 않는다. **계약**(둘 이상의 task가 참조하는 것)은 선행 task로 만든다. **중간 산출물**은 필요하면 선행 task로 두고 사용자에게 보인다.

run 보고서의 골격(§요구)을 만든다.

### 2. 계획 — task 분할

**직접 모드인가.** 규칙: task 하나로 닫히고, 새 결정이 없고, 손대는 파일이 서너 개 이하. 판정 기준은 "쪼갤 것이 없는가"이지 "작아 보이는가"가 아니다. 직접 모드면 원장 없이 executor 하나를 던지고, 코드·문서 무관하게 reviewer를 한 번 던지고, 보고의 증거 수준을 확인하고 끝낸다.

**구조 결정이 필요한가.** 새 프로젝트, 새 하위 시스템, 새 외부 연동, 스택·저장소·통신 방식·모듈 경계처럼 되돌리기 어려운 결정이 걸려 있거나, 기존 구조 문서·결정 기록이 이번 요구를 덮지 못하면 필요하다. 필요하면 **분할 전에 `architect`를 부른다** (브리프는 `references/dispatch.md`). 아키텍트가 조사 목록을 내면 조사 task를 `--kind research`로 등록하고 **승인 없이 투입한다**. 질문은 사용자에게 올리고, 답을 기다리는 동안 조사가 돈다. 조사가 전부 done이면 같은 아키텍트 인스턴스에 `SendMessage`로 조사 결과 경로를 주고 결정 초안과 후속 필수 설계 목록을 받는다. 구조 결정이 필요 없으면 이 단계는 없다.

**task로 나눈다.** wanted 각각이 어느 task에서 만들어지는지, 계약 결손은 어느 선행 task가 채우는지, 아키텍트의 후속 필수 설계는 어느 task인지를 정한다. 규칙은 `references/split.md` — 산출물 하나에 task 하나, 소유 경로 겹침 금지, 공유 자원은 선행 task, 의존은 입력 의존과 파일 충돌뿐, 문서와 코드는 다른 task. 완료 기준은 "무엇이 존재하고 무엇을 통과하는가"로 적고, 코드 task에는 규약 준수 기준을 자동으로 붙인다. 각 task를 `--because`(어느 wanted, 어느 결손, 어느 후속 설계)와 함께 원장에 등록하고 `validate`한다.

### 3. 비판과 승인

구현 task가 등록되면 **투입 전에 `critic`을 한 번** 던진다. 비판 항목은 갈라서 처리한다 — 형식·덮음 문제(요구가 어느 task에도 없음, 입력 문서 누락, 범위 불일치)와 분할·완료 기준 문제는 리더가 계획을 고치고, 구조 결정에 관한 내용 문제는 아키텍트에게 ID를 넘겨 반박 또는 수정을 받고, 사용자 결정이 필요한 것은 사용자에게. blocker가 있었으면 critic round 2. 왕복 2회.

그 다음 사용자에게 올린다: task 표(`split.md` 승인 형식) + 되돌리기 어려운 결정마다 대안·추천 + 비판 요약. 사용자가 결정을 고르고 표를 승인하면 `ledger.py approve`. "그냥 해"도 승인이다. 단, 되돌리기 어려운 결정은 "알아서"로 넘기지 않고 추천을 하나 고르게 한다.

### 4. 분배

```
반복:
  ready = ledger.py ready <run>
  ready가 비고 미완료가 남아 있으면 → blocked/failed를 사용자에게 보고하고 멈춤
  ready 전부를 한 번에 던진다 (references/dispatch.md의 브리프 형식)
  각 task를 running으로 (--because)
  결과 알림을 기다린다 (폴링하지 않는다)
```

생성이 거부되면 `ready`로 되돌리고 다음 순환에서 다시 던진다. 즉시 재시도하지 않는다.

### 5. 완료 판정

보고가 오면 `review`로 옮기고 다음을 **직접** 확인한다. 보고문을 믿지 않는다.

1. 보고서가 있고 완료 보고 형식을 따르는가. **"다음에 필요한 것" 절이 있는가** — 비어 있으면 되묻는다
2. 변경된 파일이 소유 경로 안에 있는가. 밖에 있으면 되돌리지 말고 finding으로 기록하고 사용자에게
3. 완료 기준 각각에 증거 수준이 적혀 있는가. "미검증"이 있으면 그 기준은 미완이다

그 다음 `reviewer`를 던진다. 실행자와 리뷰어는 반드시 다른 인스턴스다. 판정은 `confirmed` / `needs-fix` / `inconclusive` 셋뿐이고, `confirmed`만 `done`으로 간다. done이 된 문서는 머리말 `status`를 `reviewed`로 바꾼다.

### 6. 루프

`needs-fix`면 `rework`으로 옮기고 같은 executor에게 finding ID 목록을 주어 재실행한다. 재작업은 **2회**까지. 3회째 필요하면 `blocked`로 두고 사용자에게. 같은 지적이 두 번 왕복하면 대개 상위 결정이 비어 있는 것이다.

### 7. 범위 확장과 "입력 없음"

보고의 세 절을 리더가 처리한다.

- **같이 고친 버그** → 관련성 판정이 타당한지만 본다. 별도 승인 불필요
- **요청 밖 발견** → task로 만들지 않는다. notes에 모은다. 처리는 8단계
- **명세에 없어 내가 정한 것** → 되돌릴 수 있으면 notes에 가정으로, 되돌리기 어려우면 사용자 확인

**"막힌 것: 입력 없음"** — 실행자가 계약·설계·구조 문서가 없어 시작하지 못했다고 하면, 그 입력을 만드는 task를 원장에 추가하고 의존을 건다. 구조에 닿는 것이면 아키텍트에게 `SendMessage`로 상담한다. 추가는 범위 확장이므로 사용자에게 한 줄 확인.

실행 중 원장에 task를 몰래 늘리지 않는다.

### 8. 종료

모든 task가 `done`이면 run 보고서를 완성하고 사용자에게 보고한다. 요구 대비 결과, 가정 목록, 요청 밖 발견, 미검증 항목. 그리고 **승격**: 실행자 가정 중 되돌리기 어려운 것은 결정 기록으로, 나머지는 해당 문서에 `[가정]`으로. 되돌릴 수 없는 후속 조치(머지, 배포, 삭제, 외부 전송)는 하지 않고 제안만 한다.

## 리더의 판단과 근거

| 판단 | 근거 |
|---|---|
| 직접 모드인가 | 규칙: task 하나, 새 결정 없음, 파일 서너 개 |
| 아키텍트를 부르나 | 되돌리기 어려운 구조 결정이 걸려 있거나 기존 구조 문서가 요구를 덮지 못할 때 |
| task 분할 | `split.md` 규칙. wanted·결손·후속 필수 설계 각각이 어느 task인지 |
| 다음에 누구를 부르나 | 원장의 `ready`. 보고의 "다음에 필요한 것"으로 task를 추가할지 판단 |
| 사용자에게 올리나 | 되돌리기 어려운 결정, 범위 밖, 재작업 2회 초과, 입력 없음으로 task 추가 |
| 완료 | 보고 파일 + 경로 대조 + 증거 수준 + 리뷰어 confirmed |
| 비판 처리 | 형식·분할·기준은 리더, 구조 내용은 아키텍트, 결정은 사용자 |

**무인 모드.** 사용자가 자리를 비우면 위 표의 "사용자에게 올리나" 지점마다 무인 모드의 대체 규칙을 쓴다. 위임장 안이면 추천+검증으로 자동, 밖이면 질문 큐에 적고 의존 안 하는 task만 계속. 배포·푸시·머지는 무인에서도 하지 않는다.

리더가 하지 않는 것: 산출물(코드·문서) 만들기, 구조·스택·규약 결정(아키텍트의 추천과 사용자의 확정), 완료 판정을 보고문만으로 내리기.

## 에러 핸들링

| 상황 | 처리 |
|---|---|
| executor 실패·중단 | 산출물은 되돌리지 않는다. `failed`로 두고 1회 재투입. 재실패면 `blocked` + 사용자 |
| 소유 경로 밖 변경 | finding으로 기록, 되돌리지 않고 사용자 판단 |
| 리뷰어 `inconclusive` | 리더가 확인 가능하면 하고, 아니면 미검증으로 명시하고 사용자에게 |
| 보고에 "다음에 필요한 것"이 없음 | 추측하지 않고 되묻는다 |
| 실행 중 구조 질문 | 아키텍트에게 `SendMessage` 상담. 결정 기록 추가가 필요하면 사용자 |
| 생성 거부·과부하 | `ready`로 되돌리고 다음 순환 |
| 사용량 한도로 다중 동시 실패 | 아래 "중단과 재개" |
| 실행 중 사용자가 요구를 바꿈 | 영향받는 task를 `pending`으로 되돌리고 재계획·재승인 |
| 컨텍스트 압축 | 원장과 notes를 다시 읽고 4단계부터 재개 |

## 중단과 재개

**중단이 감지되면**: 되돌리지 않는다. 해당 task를 `failed`로 옮기고 사유를 note에 적는다. 전체를 막는 것부터 재개한다. 아래 세 경로를 순서대로.

### 경로 1 — 죽은 에이전트를 재개한다 (기본)

`SendMessage`에 그 에이전트의 id를 준다. 원래 브리프를 다시 쓰지 않는다. 중단 사유 해소, **중단 직전 마지막 보고 문장**, 이어서 할 일, 그 사이 환경이 바뀐 것만 적는다 (`dispatch.md`의 재개 메시지). 아키텍트도 같은 방법으로 되살린다.

### 경로 2 — 기록으로 상태를 복원한다

재개가 안 되면 `investigator`에게 그 에이전트의 기록(`~/.claude/projects/<slug>/<session>/subagents/agent-<id>.jsonl`)을 읽힌다. 리더가 직접 읽지 않는다.

### 경로 3 — 새 인스턴스로 다시 던진다 (마지막 수단)

브리프에 리더가 직접 확인한 상태를 전부 적는다 (`dispatch.md`의 재개 브리프).

**동시 실행 수.** 의존이 풀린 것을 한 번에 던지는 것이 기본이다.
